Existing tools for rendering-cost analysis

2026-10-12. Research for console thread T-275 #13 ("They may have related tools that solve this problem already"). The question: can existing tools tell us what each CSS or JS change costs in WebKit and Chromium, from source or at build time, or optimise it automatically, so we don't need the real iPhone for every check? Inputs came from three researchers (static/build, runtime/CI/device, engine rule tables). The writer checked every tool kept below. Lesson numbers refer to research/knowledge-distillation/README.md.

Answer first

  • Nothing existing does what we asked. No linter, build plugin or data set knows WebKit's cost rules. The one well-known property table (CSS Triggers) is archived (last push 2018-01-08). Its WebKit file marks even transform-change and opacity-change as layout + paint + composite, so it cannot tell cheap from costly. (Checked.)
  • Existing tools cover the textbook, Chrome-side half. Two stylelint plugins flag layout or paint properties in transition/@keyframes (lesson 5, part of 6). Lighthouse 13 names the animations Chrome could not composite and has a forced-reflow insight. Perfetto has Chrome's own per-frame scroll-jank SQL. All of them are free and maintained.
  • Even the textbook lists are incomplete for this page. Neither stylelint plugin lists grid-template-columns, flex-basis or stroke-dashoffset, three properties the original page animates. Neither flags steps()/linear() points, which stay on the main thread on iOS 26.
  • The only per-frame WebKit instrument is Safari Web Inspector (Timelines, Frames, Layers), and it is manual. sitespeed.io can drive Safari on a USB iPhone, but it records video and visual metrics, not frame or layout counts. No cloud device farm exposes frame timing for iOS Safari pages. Sauce Labs' jank check is Chrome only, and it reports average fps.
  • About 4 of our 30 lessons are mostly caught by existing tools, 12 partly (Chrome only, manual, or an incomplete list), 13 by nothing, and 1 is process. The 13 gaps are the WebKit layout traps, layer and blur memory pricing, work at rest, ownership conflicts (two drivers, one threshold), heat, and finger behaviour.
  • The WebKit rules a checker would need are in a handful of source files. We read them from sparse clones (§5, 16 rules with file:line):
    • StyleDifference.cpp: transform, filter and backdrop-filter none ↔ some, opacity crossing 1, dashoffset, and pointer-events;
    • KeyframeEffect.cpp canBeAccelerated: steps()/linear(), scroll timelines, composite modes;
    • CSSProperties.json: the accelerated set;
    • RemoteLayerBackingStore.mm: the backing store dropped on any size change;
    • GraphicsLayerCA.cpp: 1280 px tiling on iOS.

Fourteen of the 16 have a form a linter can see, but 1-3 only approximately (they are value conditions). Two (12-13) are runtime only. The timing-function and scroll-timeline rules already differ between iOS 26 and WebKit main, so a rule pack needs a version tag.

  • Recommendation: reuse cheaply, extend two places, build only the WebKit gap. Reuse: stylelint (two plugins, plus core restriction rules), ESLint no-restricted-syntax, bye-thrash in dev, Lighthouse user flows, and Perfetto in Chromium CI. Extend: a WebKit rule pack for stylelint, seeded from WebKit's own CSSProperties.json and our confirmed platform facts. Build: a rest-and-flip runtime probe, plus our existing costcard.mjs as the CI budget. The phone stays the final gate for anything WebKit, layer, heat or finger related.
  • Automatic optimisation does not exist for this problem. Build tools stop at images and critical CSS. The paid Motion audit grades animations in tiers, but it names no engine. The one old automatic "performance" PostCSS plugin (postcss-will-change) adds layers, the opposite of lessons 12-13.

1. How we checked

  • Status words:
    • CONFIRMED: I opened the repo, README, source or official doc on 2026-10-12 and saw the claimed feature.
    • UNVERIFIED: I did not see it; it rests on a researcher's background knowledge or a vendor claim.
  • Release dates: from the npm registry (npm view) or GitHub releases (gh api).
  • What was not done: nothing was installed into a project or run against our page. "Catches lesson N" means its rule list or docs cover the mechanism, not that it fired on our build.

2.1a The two stylelint plugins' exact lists (read from cloned source)

stylelint-high-performance-animation (index.js, commit c890435, 2026-03-09):

  • What it checks: transition-property (l.177), transition (l.201) and declarations inside @keyframes (l.274).
  • all: transition: all is flagged (l.184, 224-244).
  • Option: ignore: "paint-properties" drops the paint list.
  • propsThatCauseLayout (l.36-110):
    • position and insets: position, top, bottom, left, right, inset-block-start/-end, inset-inline-start/-end;
    • sizes: width, height, inline-size, block-size, and every min-/max- size;
    • padding and margin with every side;
    • display, border-width, border-spacing, border-collapse, border;
    • fonts: font, font-size, font-family, font-weight, font-style;
    • float, overflow, overflow-x/-y/-block/-inline, line-height, vertical-align, clear, white-space, list-style, list-style-type, zoom, content, box-sizing;
    • text: text-shadow, text-align, text-indent, text-transform, text-overflow, word-wrap, letter-spacing;
    • appearance, direction.
  • propsThatCausePaint (l.112-130): color, border-color, border-style, border-radius, visibility, text-decoration, background, background-color, background-size, background-image, background-position, background-repeat, outline, outline-style, outline-width, outline-color, box-shadow.
  • Not in either list:
    • grid-template-* and flex-basis: the "o" and the avatar exit (lesson 5);
    • stroke-dashoffset and every SVG property: the accent word (lesson 6);
    • filter, backdrop-filter, clip-path, mask.
  • Never looked at: timing functions. It parses them only to skip them (l.14-24).

stylelint-plugin-css-performance-budget (src/rules/, commit 0ef7be2, 2026-10-05):

  • no-layout-thrashing-properties (l.46-83, transitions and keyframes):
    • bottom, height, left, right, top, width;
    • inset, inset-block-*, inset-inline-*;
    • margin and padding with every side and logical form;
    • max-height, max-width, min-height, min-width.
  • no-expensive-animation-properties (l.69-81): -webkit-backdrop-filter, backdrop-filter, background-position, background-size, box-shadow, clip-path, filter, mask, mask-image, mix-blend-mode, text-shadow.
    • Thresholds: filters are reported only past maxFilterBlurRadiusPx 30, maxFilterFunctions 4, maxShadowBlurRadiusPx 48 or maxShadowLayers 3 (_internal/paint-cost-analysis.ts l.36-41).
    • transition: all is flagged unless allowTransitionAll.
    • Keyframes are checked by default (l.118).
  • no-will-change-abuse: more than 5 properties (l.44); the keywords all, contents, scroll-position (l.45-49).
  • Not in any list: grid-template-*, flex-basis, border-width, stroke-dashoffset, steps()/linear().

4. Gaps, with evidence

1. No WebKit cost rules anywhere outside WebKit's C++.

    • Evidence: CSS Triggers is archived and wrong for WebKit (§2.4), and both stylelint plugins are engine-neutral lists.
    • The rules behind lessons 6-9 (dashoffset as SVG layout, presence flips, size-container restyle, contain: layout not a boundary, iOS 26 steps()) live in StyleDifference.cpp, RenderObject.cpp and KeyframeEffect.cpp. Section 6 of the distillation cites them.
    • The only machine-readable piece is the acceleration list in CSSProperties.json, and the accelerated set moves between versions (WebKit bugs 250970, 253315). So any table needs a version tag.

2. Conditional costs are not property costs. The engine researcher's point stands. Most of our WebKit costs depend on values and state, not on the property name:

    • opacity crossing 1;
    • none to some;
    • a layer's size change discarding its backing store;
    • sub-pixel offsets;
    • sync image decode on an already painted layer.

A linter sees the stylesheet, not the value at frame N. These need a runtime probe or the device. 3. Scroll context. A "cheap" scroll timeline still restyles every target each update on WebKit (fact 23). A reveal's cost depends on what else flips at the same y (lesson 14). The toolbar resize exists only on iOS Safari with a finger (lesson 9). No tool models where on the page work lands. Perfetto does this per scroll update, but only for Chrome. 4. Layer and blur memory pricing. Web Inspector's Layers tab shows count and MB per layer, but only manually, and it has no "built in the first frame of this interaction" view (lessons 12-15). No tool prices a layer or blur before the build. Chrome's GPU memory overlay is Chrome's, not Core Animation's. 5. Work at rest and ownership.

    • No tool parks the page at each scroll position and asserts zero rAF, style, layout and paint (lesson 18).
    • No tool detects two drivers on one property (lesson 4), JS running effects CSS disabled (lesson 3), or one threshold with several owners (lesson 14).
    • All four are detectable in a dev-mode probe (getAnimations(), a rAF hook, MutationObserver, transition events).

6. Per-frame WebKit counts in automation.

    • What exists: LoAF is not in Safari, Playwright's WebKit is not Safari and has no tracing, sitespeed.io gives video and visual metrics only, and Sauce Labs is Chrome only.
    • Our own iphone.mjs and frames.mjs already produce frames over 34/50 ms by scroll position on a real iPhone. We found no public equivalent.

7. Heat, finger and perception (lessons 19, 22, 24, 26): no web tool. These stay human and device work.

What this means for a checker:

  • Rules 1-11 and 14-16 have a form a linter can see (CSS for most; ESLint for 7 and 16). A WebKit pack can encode them from these lines with a version tag.
  • Rules 1-3 are value conditions. A linter can only flag likely cases: an end or rest value of 1/none beside an animated side. The real test is runtime, which is why the rest-and-flip probe (§6, Build 1) exists.
  • Rules 12-13 are runtime only. They need sizes and the composited state, which only the engine knows. WebKit's Layers tab shows both.
  • Rules 10-11 move between versions. On WebKit main, threaded animations (default on) lift the steps()/linear() and scroll-timeline exclusions. A rule pack must key on the target iOS version and say UNRESOLVED for versions nobody has checked.
  • No WebKit rule here gives a cost in ms. The source says which stage runs, not how long it takes. Size, layer count and frame sharing set the time (lessons 12, 30), and that number still comes from the phone.

Extend (the one place an existing tool should grow)

A WebKit rule pack as a stylelint plugin. It is small, and our sources already exist.

  • Seed: CSSProperties.json animation-wrapper-acceleration (version-tagged), plus our CONFIRMED facts 3-7, 16, 18, 20, 23.
  • Rules:
    • animated property not in WebKit's accelerated set;
    • steps()/linear() points in animations (iOS 26);
    • stroke-dashoffset, SMIL and background-position animation;
    • var() inside @keyframes;
    • keyframes or rest states ending on opacity: 1, transform: none or filter: none next to an animated side (lesson 8);
    • container-type on an ancestor of animated or typed text (lesson 7, within one file);
    • contain: layout without size used as a boundary (fact 20);
    • aspect-ratio + height: auto cards inside a sticky ancestor (lesson 9, heuristic);
    • animated width/height/border-radius/blur on an element that also has will-change or a filter (lesson 11).
  • Base: contribute the property-list fixes (grid-template-columns, flex-basis, stroke-dashoffset) upstream to stylelint-high-performance-animation, and keep the WebKit rules in our own plugin. Upstream is engine-neutral by design.

Build (only the gap)

1. Dev-mode rest-and-flip probe (lessons 3, 4, 8, 14, 18), a small client script loaded by a Vite plugin in dev and in the Playwright runs. It reports:

    • running animations and rAF fires while parked at each scroll position (goal 0);
    • two writers per property: an inline write while a transition on that property is active;
    • elements whose computed opacity reaches exactly 1, or transform or filter none, at an animation end;
    • several state changes inside one scroll-position bucket.

It runs in any engine, so the same script works in Safari on the phone or the Simulator. It replaces nothing on the phone; it finds candidates. 2. CI budget = our cost card. tools/costcard.mjs already turns Chrome traces and Simulator Timelines into layouts, paints, layers, memory and rAF per element and event (lesson 30, memory less-work-landing-rule). Wiring it into a CI job with fixed budgets is the "budget in CI" checklist item (distillation §5, Guardrails). Nobody publishes this. 3. Not worth building: a static per-property ms table. The costs are conditional (gap 2), engine-version dependent (gap 1), and frame-shared (lesson 30). A table would give false confidence. Also skip automatic rewriting: the safe rewrites (FLIP for size, opacity: 0.999 rests, linear ramps for step-end) each needed a pixel check and sometimes a user decision (lessons 5, 6, 29).
