The map

Part 1 tells how this loop grew. Part 2 shows what it found in the page. This part is the wiring diagram: the pieces an engineer would need to build a similar system, each with the incident or user request that made us add it.

The setup is small in hardware and large in agents. One Mac runs Chrome and the iOS Simulator. One real iPhone sits on the desk. One person, the user, owns both and makes every decision about how the page should look. Everything else is Claude Code sessions: one lead in the main checkout and many workers, each in its own git worktree.

Two design choices hold the rest together.

  • Shared state lives in the git common directory, not in commits. A worktree sees a committed file only after the lead lands it and the worktree rebases. A lock, an incident or a user message has to be visible to every agent the moment it is written, so tools/lib/store.mjs keeps them as JSON files under .git/fastwork-mirror/, with writes serialized by the lock library's guard. It is local by construction: nothing in .git/ is pushed, and nothing is ever pushed anyway (Hard rule 2).
  • Every rule names what enforces it. The agent guide lists twelve hard rules. Each carries a Why and an Enforced line that names the hook, deny rule or tool refusal behind it, or says "convention". An agent can tell which rules will stop it and which depend on its own care.

Each role is a Claude Code agent definition with its own model, effort and tool list. The table is the short form of the roster. The column that matters most is the last one: who may run the devices. Named spawns in their own worktrees

Every spawn gets a name of the form <role>-<topic>: fix-scrollcb-g0, ts-i170, review-blur, map-deck-contain-webkit. The name is the address for SendMessage, the owner field on a lock, the author on a console post and the key on the status board, so one string ties an agent's messages, holds and rows together. A memory note reminds the lead to check the first spawn after each context compaction, because a nameless spawn is unreachable by its peers.

A worker runs in .claude/worktrees/<name>/ on its own branch. The baseline (a 61 MB frozen copy of the page) is not checked out there: fix.mjs new makes the worktree sparse and the tools read the main checkout's copy through git rev-parse --git-common-dir. A fix changes Fastwork's code only in a gitignored overlay folder, and serve.mjs --overlay serves overlay files first and the frozen baseline for everything else.

Peer messages and hand-backs

  • Results go to their consumers. A fix owner sends a result straight to the integrator of the next best build, to mgmt-ops for card reads, and to mgmt-devices when it changes what a device can start next. The lead gets one FYI line. This rule (user request T-160) removed the lead as a relay.
  • A blocked worker ends its run with a report the lead can resume. The template is three lines: what it is blocked on, what is done and not done, and the exact command to resume with. When the incident is fixed, a SendMessage by name resumes the agent with its history intact.
  • Delegated authority is written down per role. A fix owner decides its next probe and answers the user in its own threads. mgmt-devices reorders the Mac queue inside the board's priority order and releases an idle phone hold, with every action audited. Only the lead lands fixes, signs the attribution card and changes rules.

The lead coordinates incidents itself, by design. Teammates cannot spawn teammates, landing happens in the main checkout, and every permission prompt surfaces in the lead's session. A separate coordinator agent would add one hop to every decision and remove none.

Shared devices

Frame timing on a laptop is fragile. One npm test beside an A/B run can shift a verdict. So every device sits behind a lock in the shared store, and every lock is a queue with rules about who may run beside whom.

The chrome-measure lock

  • FIFO with process holders. verify.mjs and fix.mjs ab take the lock themselves. A holder is a live process (stale when its pid dies) or a lease with a time limit. A waiter not seen for 30 s is skipped at a hand-over but keeps its place.
  • Host gate. A timing hold starts only on a quiet Mac: CPU at most 25 % over 10 s, load average at most 6, normal memory pressure. After 600 s it starts anyway, and its runs are marked contaminated.
  • Short lane. A job capped at 300 s (a commit's test run, a counts-only probe) is served before earlier normal waiters at the next hand-over. It never preempts the holder, and run kills its whole process tree at the cap.
  • Shared lane. Jobs that time nothing run together: weights 1 for a probe, 2 for npm test, 3 for a Simulator session, up to a cap of 3. Anything timed refuses to start inside a shared slot.
  • No-timing holds. A build or other CPU work takes a normal turn but skips the host gate, and nothing timed may run inside it.
  • One hold, not a lease. An agent measures the A/B and its probes in one lock.mjs run … -- sh -c '…'. Tools started inside re-enter the hold instead of queueing behind it. That rule came from a deadlock (I-005).

The iPhone hold

The phone is one physical device that shows one page at a time. Agents cannot take a phone lease at all. They run their phone part inside lock.mjs run iphone --owner <me> -- <part>, and the hold lasts exactly as long as the command (I-168). --keep 120 lets the next part continue the same hold. --block <ticket> --max-seconds 3600 marks a timed block. An agent that is not ready yet queues with --not-ready: it keeps its place and is never served. That rule exists because agents used to take the phone before their pre-data read was done and leave it idle (I-155).

Inside a hold, iphone.mjs drives Safari over the WebKit debug proxy and a WebDriverAgent gesture runner. Every run records its own frame stamps on the phone, so a phone run can coexist with light Mac work. Outside its own Mac hold, a phone run refuses (WAIT) beside another agent's normal Mac hold.

The Simulator, and when the phone is not needed

A standing user rule: a job that needs an iPhone but no performance number (DOM checks, gesture dry runs, pixel parity) runs on the iOS Simulator in a shared slot of weight 3. The real phone is kept for timing and for the user's own fingers. Simulator timing is never a verdict.

Phone blocks

  • Only ticketed builds go on the phone, served from immutable snapshot copies whose hashes are on the ticket.
  • A block asks one question against one named control on the same base: one uncounted warm-up per arm's port, then at most 9 counted runs in the order C V V C C V V C.
  • Sentinels are control runs at the block's start and end that must reach a fixed smoothness. A failing sentinel voids every run since the last passing one, because a hot phone looks like a slow build.
  • Between blocks the phone cools by battery temperature, read from the device, at most 10 min. A block runs at a named heat profile. Today's default is a thermal state induced by Xcode, so phone checks start warm the way real phones are used.

Protocol v2: cards before data

Version 1 let agents measure first and explain afterwards. On one day it produced thirteen distinct mistakes. One model predicted a 30-45 ms gain that measured 6-9 ms. One ablation removed a blur from the wrong element and measured nothing. One logger capped events at 12 per frame and invented a cause. Protocol v2 turned each mistake into a rule, and put a signed card in front of every stage.

StageQuestionGate
RWhere and how often is it slow?At least 3 phone runs of one driver plus Chrome; clusters by "crossing", the nearest code threshold, because Chrome and phone scroll positions differ by about 77 px
IWhat changes in that frame?Hypotheses as element + selector + property, each proved by computed style in Chrome and in WebKit
DWhich mechanism, on which device?A positive ablation, at least one negative sibling, a mechanism check per arm, the axis the frame is locked to, and one run that moves that axis apart. Every platform claim it rests on is CONFIRMED against a reference, never only OBSERVED
FDoes the build do only what we intended?Build card, prediction card with an interval, ledger row, slot ticket
VA win on the target device and no regression elsewhere?Review report, idle checks at three positions, every position bin on both devices
LRebase and fast-forward, tool fixes first

Signed before the data, ruled before the run

A phone check card fixes the primary metric, its limit, the decision for each outcome and the reader script before any run. The kit is frozen by hash. The lead signs it with rulings: amendments that settle open questions before anyone can see which way they cut. The card for today's best build, P-174, carried five:

  1. The primary as drafted: frames over 50 ms per run, median difference V minus C at most +2 in both scroll windows, and both twin thresholds must agree, else the verdict is OPEN.
  2. A misfire stops the block: any blurred frame on a fast flick that triggered the new code stops the runner before landing.
  3. A gate fix for Chrome pixel checks is accepted and its remaining difference disclosed.
  4. The page log records how many deck photos are complete at the moment of each flick. This was the only kit change after signing. It was checked on the Simulator first (control 7 of 26, variant 26 of 26) and re-hashed in the signature commit.
  5. Safety: cool below 40.0 °C before every hold, stop at 43.0 °C or a Critical thermal state, check the gesture driver first, repair link failures inside the hold.

The twins are the same count at ±4 ms around each threshold (46 and 54 ms around 50). A verdict that flips between twins is reported as threshold-sensitive, never as a result. Part 2's casebook shows how to read these numbers; here they matter as machinery: the card names them in advance, the reader computes them, and nobody chooses a threshold after seeing the data.

Platform claims

Any browser behaviour found by our own probes is OBSERVED, written as "in our setup, cause unknown". Before it can carry an attribution card, a verifier checks it against a spec, official docs, engine source or the bug tracker, and returns CONFIRMED, REFUTED or UNRESOLVED with the decisive local check. The lead does not sign NAMED on an OBSERVED claim, and never passes one to the user as fact.

The user console

The user never reads agent transcripts. Everything the user must do or answer goes through one local page, served on localhost by the lead with nohup so it survives the session's background-job limit. It has five tabs.

Your steps: actions with parts

A step is something only the user can do: swipe two pages, answer yes or no, start Xcode. A step has parts, and each part has a small state machine.

  • Gate. Start stays grey until the runner acks ready, so the user never swipes a page that has not loaded.
  • Record. After Start the page says "don't swipe yet" until the runner acks recording; then it says "swipe now". The recorder is pre-armed so this takes seconds.
  • Start over. Two taps reset every part to a new attempt. The runner's waits exit with code 5 (REDO), and an ack from an old attempt is refused, so late messages from a previous try cannot advance the new one.
  • Runner-ended parts. A part the runner finishes itself shows "Running, please wait; this ends by itself" and refuses the user's Done.
  • Blind pairs. A swipe pair hides both URLs; the A/B order lives in private metadata that only the waiting agent reads back.

One phone step at a time: only the holder of the phone may post a phone step, and only while no other phone step is open. This rule came from a morning where four steps from different agents piled onto the phone (I-123, below).

Threads: routing, triage, listeners

Threads are where the user asks and agents answer. Before routing existed, the measurement was blunt: in 24 hours, all 88 of 88 user messages woke the lead, and 13 of the 20 messages in threads already assigned to another agent were still answered by the lead. The router now picks the first listening, free owner.

Three refinements came from misses:

  • Orphan waits (I-163). A listener process can outlive the agent that started it. The router walks the wait's parent chain and counts it only if a live Claude Code process is still on it.
  • Deaf owners (I-169). An agent inside a long foreground command reads no messages until it ends. The router reads the agent's transcript, and an owner inside one foreground call for more than 30 s counts as deaf.
  • One line per wake (I-147). A listener runs as one persistent Claude Code Monitor on thread wait --monitor, which prints WAKE <kind> <id> <text>. Earlier listeners filtered their own output and dropped a proposal decision for 16 minutes.

The answer-format linter

The user found early answers hard to read: long paragraphs, unexplained ids, the action buried in the middle. The fix became a memory rule (answer first, short bullets, plain words, numbers in small tables, about 10 lines, "What you need to do" last), and then a linter in tools/lib/answer-lint.mjs. The console refuses to post a reply that fails it:

  • the last line does not start with "What you need to do";
  • more than 18 non-empty lines, or a line over 250 characters (calibrated on the 227 earlier replies: 250 characters still catches the two the user complained about and would have refused 16 % of them);
  • an internal id such as PR-041 or a commit hash with no plain words explaining it;
  • a pipe table without its separator row, which the page would print as raw pipes.

Proposals with Try-it pages

Anything that changes what the page looks like, even slightly, is the user's call. An agent posts a proposal: the problem, what stays the same, the risk, and two or three options with measured gains, each tagged OBSERVED, CONFIRMED or UNRESOLVED. Every option carries a Try-it panel: A and B served as real pages. proposal phone <id> serves them on the Wi-Fi so the user can fling them on the iPhone. Screenshots alone were refused twice before this became a rule.

A decision is the spec. "Changes requested" means revision N+1 of the same proposal with every point of the note answered, and the page shows who is revising and by when. An overdue revision opens an alarm thread for the lead.

Status board, idle alarms and the steward

Every workstream has one row with a state (researching, measuring, waiting, ready-to-land, parked and so on), a plain-words note and, when waiting, what it waits on. The board adds what it can see by itself: queue position on each lock, held devices, open user steps, blocking incidents, and readings from transcripts such as "owner ended" or "deaf: in npm test for 4 min".

The idle alarm (I-105) fires when the phone has been free for 5 minutes, or the Mac lock for 10, while work waits for it. A phone holder whose only activity for 2 minutes is waiting on another lock is reported as stuck. Alarm threads go to a steward, mgmt-devices, and never to the busy workers; the steward reads the holder's processes and sends one exact correction (I-175). On one day the lead had noticed idle phones only after the user did, 18 alarms and 204 idle minutes. The steward has an exit target: two 3-hour windows in a row with at most 2 idle minutes, after which it parks and the tools carry the job.

The Best build page

One tab answers the question the user asks most: what is the best build today? It reads fixes/BEST_BUILDS.md and fixes/PROGRESS.json: each version, what it added, how it was checked, and a Try-it link that serves exactly the tested bytes on the phone. The lead updates it at every build change.

Incident and findings boards

Anything that breaks outside an agent's own topic is an incident: a tool crash, odd numbers, a stuck lock, a disconnected phone. One report per problem, one fixer, and everyone affected hears when it is fixed.

# any agent
node tools/incident.mjs open --by fix-nav-earn --title "fix.mjs ab crashes after run 3" \
  --error "<first error line, verbatim>" --class tool --blocking yes --workaround "…"
#  OPENED I-004   new: message the lead
#  JOINED I-003   already reported: use its workaround, don't fix it in parallel
#  KNOWN  I-002   fixed on main: git rebase main, retry
node tools/incident.mjs wait I-004 --timeout 3600   # in the background; exits with the announcement
  • The dedup key is the first error line with paths, numbers and hex ids masked, so a second agent hitting the same crash joins the first report.
  • The lead triages in one line (class, priority, owner, workaround) and spawns a toolsmith per incident as ts-i<nnn>. It reproduces, writes a failing test, fixes, and delivers one tools: commit.
  • The lead lands it after running the full suite in the main checkout, then resolve prints the announcement: the commit, the rebase check, and "Re-measure" when measurement code changed and older A/B results no longer compare.

The findings board is the same idea for knowledge. Any agent, read-only reviewers included, posts a technique that won, a pitfall, a code coupling or a measurement surprise. A near-duplicate gets SIMILAR F-007. Agents read unread findings at start and acknowledge each one with "applied in <topic>" or "not relevant". Two of today's, from the people-deck work: F-370 (a time-based reveal fade looks like a blink under a fast fling) and F-371 (decoding images ahead moves their paint cost into the reveal frame).

The enforcement layer

Rules in a prompt are suggestions. Each rule that matters has a mechanism below it, and the agent guide forbids working around any of them: if one blocks legitimate work, the agent stops and asks.

LayerWhat it stopsWhy
git hooksMerge commits (even with --no-verify, via reference-transaction), pushes, staged overlays, keys, measurement output, and any snapshot change that is not authorizedLinear history: each fix is one contiguous series that can be bisected or reverted
git-guardA Claude Code PreToolUse hook that parses the shell command: splits &&, pipes, sh -c, heredocs, wrappers and git aliases, then denies push, non-fast-forward merges, hook overrides, curl to GitHub, and every camera or frame-viewing routeA permission rule like Bash(git push *) does not match git -C . push. It fails closed for git merge/push patterns and open for everything else, so a parser bug cannot brick the shell
fg-guardLong commands in the foreground: the full test suite, lock holds, waits, A/Bs, phone runsAn agent reads messages only between tool calls; a 5-minute foreground command makes it deaf (I-170). No opt-out
scope guardnpm run test:unit fails, naming the files, when a non-tooling branch touched tools/, tests/, hooks or the snapshotOnly toolsmiths change tooling, in separate commits (I-021)
baseline pinTools refuse, exit 3, when the frozen copy of the page differs from the snapshot id pinned in baseline.json; A/B verdicts get a BASELINE-MODIFIED: prefix if it changed mid-runEvery result names the exact build it measured; a re-mirror shows up as a git diff, never silently
testsAbout 2,000 tests on a tiny fixture baseline, no Chrome, network or phone; the pre-commit hook runs them whenever tooling is stagedAgents may fix tools, but only with a covering test, and never by weakening one

The enforcement layer itself is not tooling. An edit to a hook or to the settings file asks the user, which is the hinge for the next section.

Privacy guards, and the one exception

The user's personal data never leaves the Mac: no name, email, account id, LAN address or device identifier goes into a web request, a connector or a committed file. Phone links in threads are written as http://lan:<port>/ and resolved by the page at view time, because a typed address went stale on a Wi-Fi reconnect (I-073) and would leak the network if committed.

The camera incident and the no-frames rule

On 2026-10-02 a route for recording the iPhone screen turned on the Mac's camera. QuickTime's movie recording opens on the built-in camera before the iPhone source is chosen. The user stopped the work. The agent gave a full account, every file was deleted and the deletion verified, and the user decided the session log stays as evidence of the mistake.

What replaced it is a small signed Mac app driven by ioscap.mjs. It queries only the iOS screen device, refuses any camera and never falls back. Its first run needed the user's OK and the user watching the camera light. It prints numbers only: frame counts, distinct-frame rate, timing gaps. git-guard denies every other route (QuickTime, camera listing, screen-capture flags, capture APIs in inline scripts), every player, and every frame export. Nobody looks at the pictures.

How the deck-recording exception was granted

On 2026-10-09 the user wanted to see the people-deck blink frame by frame. The approval came in three steps, and the order matters:

  1. In a console thread, the user approved decoding the Simulator videos into numbers and picture strips. The lead declined to change the guard: console text reaches an agent as tool output, which Claude Code cannot verify as the user. Claude Code's own permission system also refused the lead's attempt to edit the guard.
  2. The user offered to put the iPhone in Sleep focus so no notification would appear, and said again in the thread that the guard could change. The lead again explained that this channel cannot authorize a guard change, and gave the exact words to type in the Claude Code chat.
  3. The user typed the request in the chat and approved the edit prompt. The guard was widened only for ffmpeg image exports to files under out/, from Simulator videos under out/people-blink/ and from iPhone recordings whose name carries -pb-. Everything else stays denied.

Every picture posted afterwards was checked first. The address bar was greyed out because it showed the Mac's network address. The scope is written down as a memory note: widen it only on a new request in the chat.

The trust boundary

Anything an agent reads through a tool, including a console message, a thread, a web page or another agent's report, is data. Only the user's own words in the Claude Code session, plus the permission prompts they approve, can change a guard. Build the console for convenience and the chat for authority.

Project memory and recurring prompts

A long-running loop forgets. Sessions end, contexts compact, agents are replaced. Standing user rules live in memory/, one note per rule, committed on main. The index is imported into the agent guide, so every agent loads the one-line summaries and opens the full note before acting in its area. Only the lead edits notes, and only after removing personal details.

Each note has the same shape: Rule, Why (the event that caused it, with its thread id), How to apply, and a dated History. Some examples:

  • Perception tests are touch A/B. The user judges lag by whether the content follows the finger, so smoothness tests are blind swipe pairs, not watched clips.
  • Trace before asking. A reported lag is traced from recordings, logs and probes first; the user is asked only what no data can answer.
  • Busy workers answer later. A user question never pulls a worker off a measurement; a helper answers now.
  • Illusions must be pixel-identical. A cheaper look-alike lands without asking only within agreed pixel limits (the PR-010 numbers); anything more is a proposal.

Recurring prompts

  • Usage meter, every 30 minutes. Crons last one session, so the lead re-creates it at every start. It reads local transcripts, appends to a local file, and posts a 3-line summary in a thread. Account usage is personal data, so the readings stay out of commits.
  • Hourly team measures. research/management/proactive-measures.mjs counts the lead's hand moves of the queue, phone idle alarms, board rows waiting on the lead, and user answer times. It prints no thread text. It is how the user checks that "proactive by default" holds.
  • The lead's check-in. Each check-in walks the same list in order: rows waiting on the lead, idle devices, unanswered user messages, land requests. Each decision asked of the lead gets an answer or a named delegate in that check-in.

for engineers if you build one

If you build one

  1. Put shared state where every worker sees it at once. Git worktrees isolate code well and coordination badly. A small JSON store in the git common directory gave us locks, incidents, threads and a status board for every worktree, with no server.
  2. Give every rule an enforcer, and say which ones have none. Parse shell commands in a PreToolUse hook, because pattern rules miss wrappers. Fail closed on the few patterns that matter and open on everything else.
  3. Lock devices by kind of work. Timing work needs a quiet machine; functional work can share. Encode that in the lock instead of in agent manners, and let a hold be a process, so it ends when the work ends.
  4. Sign the reading before the data. A card with the metric, the limit, the decision per outcome and a frozen reader removes the temptation to pick a threshold afterwards. Rulings settle the open questions while nobody knows which way they cut.
  5. Give the human a console, and route it. Steps with gates and Start over, threads that reach a listening owner, a linter that keeps answers short, and Try-it pages for every look change. The user answered dozens of questions a day without reading a transcript.
  6. Keep authority in the chat. A console message is convenient and unverifiable. Changes to guards and rules happen only on the user's own words in the Claude Code session.
  7. Turn every complaint into a note with its why. Memory notes carry the event behind each rule, so a fresh agent knows what the rule protects and where its edges are.
