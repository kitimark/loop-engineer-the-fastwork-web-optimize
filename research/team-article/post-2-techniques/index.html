Sixteen Milliseconds · Part 2

The Casebook

Ten worked cases from making one marketing homepage scroll smoothly on an iPhone 15 Pro Max. Each case gives the symptom, how we measured it, the root cause with the engine source where we could find it, the fix with its numbers, and what the fix cost.

Part 1 tells how a team of AI agents and one person ran this study. This part is for web developers who want the techniques. The page is fastwork.com's homepage, frozen as one snapshot so every number below measures the same bytes. The current best build is called g0.0l. Every case below is a change that is in it, or a lesson we needed to get there.

The unit of everything below

One frame on the phone is 16.7 ms. The goal was zero frames over 50.

Safari on the iPhone updates the page at about 60 times a second, so an on-time frame is 16.7 ms apart from the last. We counted the gaps between frames. A gap over 50 ms (three frames' worth) is what the user called lag, and the target was none. A gap over 34 ms is the secondary count. Because a frame of 49 ms and one of 51 ms are not really different, every count also comes with its twins at ±4 ms.

Case 01ScriptStyleLayoutPaintComposite

Hand the motion to the compositor

Countdown roll (PR-017) · end-of-page menu morph (PR-030, in g0.0k and g0.0l)

Symptom

Two things on the page moved from script on every frame: the countdown's rolling digits and, at the end of the page, the menu bar that grows into a full panel as you keep scrolling. Both stuttered whenever the page had other work, because they could only move when the main thread finished a frame.

How we measured

  • Chrome 154 traces (430x932 DPR 3): countdown callbacks per roll, and main-thread frames with every other animation frozen.
  • Simulator Timeline: paints and layouts per menu open.
  • iPhone block P-157 (driver G, 4 runs per arm, Timeline on): Layout, Paint and style records per menu frame.

Root cause

Each digit ran its own requestAnimationFrame loop: a spring stepped in 16 ms substeps, writing transform inline every frame. The menu morph wrote sizes, radius, blur and colours from a scroll callback. Every one of those writes costs a style pass, and the size writes a layout and a repaint, on WebKit's main thread.

The engines can run an animation without the page at all. WebKit builds an accelerated animation as a Core Animation animation in the UI process, and the web process doesn't tick it while it runs CONFIRMED (WebKit KeyframeEffect.cpp canBeAccelerated l.1926-1971, safari-7624 branch 0f8c6795). Safari on iOS 26.4+ also runs qualifying scroll-driven animations on the scrolling thread CONFIRMED (webkit.org/blog/17862; UnifiedWebPreferences.yaml 8316-8329). Only transform, opacity, filter and backdrop-filter qualify.

Fix

For the countdown: sample the same spring once at 60 Hz and hand the samples to the engine as keyframes. The motion is the same; nothing runs per frame.

// Before: one style write per frame, from script
function roll(cell, from, to) {
  const t0 = performance.now();
  requestAnimationFrame(function step(now) {
    cell.style.transform = `translateY(${spring(now - t0, from, to)}px)`;
    if (!settled(now - t0)) requestAnimationFrame(step);
  });
}

// After: sample the spring once, let the compositor play it
function roll(cell, from, to) {
  const frames = [];
  for (let t = 0; t <= SETTLE_MS; t += 1000 / 60)
    frames.push({ transform: `translateY(${spring(t, from, to)}px)` });
  cell.animate(frames, { duration: SETTLE_MS, easing: 'linear', fill: 'both' });
}

For the menu: every part follows the scroll through keyframes on a view timeline. One function computes each part's transform, opacity and filter for a morph value, and generates the keyframes from it. The changing rounded corner has no transform form, so it is rebuilt from four corner clippers, each scaled by r/32 and counter-scaled inside.

.menu-zone { view-timeline: --menu block; }
.menu-part {
  animation: grow linear both;          /* the shorthand resets the timeline, so: */
  animation-timeline: --menu;           /* longhands come after it */
  animation-range: cover 0% cover 100lvh;  /* survives the toolbar */
}
@keyframes grow { from { transform: scale(.42); } to { transform: none; } }

Cost and caveats

  • Style stays. Every rendering update ticks every active scroll-driven animation and invalidates its target's style CONFIRMED (AnimationTimelinesController.cpp 140-180, WebAnimation.cpp 1554-1576). The phone agrees: style recalcs went up, not down.
  • Layout did not go to zero. The prediction was at most 0.3 per frame; the phone measured 1.00-1.04. Simulator call stacks found why: of 291 layouts forced inside script, 158 came from elementsFromPoint in a hit test and 44 from reading window.scrollY OBSERVED. On WebKit, reading scrollY while layout is dirty forces a layout CONFIRMED (LocalDOMWindow.cpp 1477-1481). The compositor can't remove a read your script makes.
  • No frame-time gain on the phone in this block: frames over 50 ms per menu frame overlapped (0.1-0.3 % vs 0.2-0.5 %) OBSERVED.
  • Starting is not free. Starting an accelerated animation on an element that is not yet composited forces a compositing update on the main thread CONFIRMED (KeyframeEffect.cpp 2015-2017, RenderLayerCompositor.cpp 3813-3830). The countdown's phone check (P-093, driver W) found +1 frame over 50 ms per run near the top, 0 in every C run and 1-2 in every V run, within its no-worse limit; cause untested.
  • Not every easing qualifies. Time-based animations with steps() or linear() with points stay on WebKit's main thread on 26.x CONFIRMED (canBeAccelerated). Keyword linear between dense keyframes is fine.
  • Big blurs can get slower. Making a full-screen 14 px blur eligible for the compositor doubled the next frame's Composite (phone 74 vs 42 ms) OBSERVED. Count Composite, not only Paint.
  • WebKit asks Core Animation for 80-120 Hz on every animation it creates CONFIRMED (PlatformCAAnimationRemote.mm 609-613), but whether our phone actually drew them faster than 60 Hz is UNRESOLVED.

Case 02ScriptStyleLayoutPaintComposite

Size the deck with container units, not aspect-ratio

Build g0.0j · CSS only, phones and touch screens · finding F-366

Symptom

Dragging a finger down the page, frames over 34 ms bunched up between y 1000 and 3400. Nothing visible changed in that stretch; the page was just scrolling.

How we measured

  • A Simulator cost map: at every 200 px from the top, a 1 px programmatic scroll out and back, and the largest Layout record in the next 300 ms. A programmatic scroll marks sticky and fixed boxes dirty the same way a drag does.
  • Knock-out arms: CSS that removes one suspect at a time, added after load. They change the look, so they are for attribution only.
  • Simulator robot-finger drags, then iPhone block P-172 (driver G, 4 runs per arm, Timeline on).

Root cause

Every 1 px nudge cost a 20-35 ms layout while either of the page's two sticky boxes existed. Making both non-sticky removed it; either one alone kept it. Hiding the people section's profile deck removed it too. The deck holds six cards side by side in a horizontal snap row, each sized like this:

.deck  { display: flex; overflow-x: auto; scroll-snap-type: x mandatory; }
.card  { flex: 0 0 100%; aspect-ratio: 353 / 764; height: auto; }
Knock-out (Simulator, y 800-3400)Largest layout per nudge
Control: both boxes stickymedian 22.7-25.7 ms
Both boxes made non-stickymedian 0.5 ms
Deck hidden0.5-0.7 ms
Only the active card shown9.7-15.9 ms (scales with card count)
Cards at the same fixed height, no aspect-ratiomedian 0.4 ms

The source explains half the chain. When the layout viewport moves, WebKit marks every fixed and sticky renderer for layout CONFIRMED (LocalFrameView.cpp 3822-3834, WebKit main e64e2891). A full block layout re-dirties its percent-height descendants and invalidates the preferred widths of aspect-ratio boxes on that chain CONFIRMED (RenderBlockFlow.cpp 588, 638, 807-841). Which link carries a sticky box's layout into the deck's cards is UNRESOLVED; the knock-outs carry the attribution.

Fix

Give the cards the same height without asking them to derive it from their own layout. The deck becomes an inline-size container and the height comes from its width:

.deck { container-type: inline-size; }
.card { /* aspect-ratio removed */ height: calc(100cqi * 764 / 353); }

The card is the deck's full content width, so this is the same box: 844.078125 px tall at 430 px wide, in both builds. container-type: inline-size adds only style and inline-size containment, no layout or paint containment CONFIRMED (StyleComputedStyle.cpp 458-468, WebKit main e8c36a19). The one new constraint is that the deck's width can't depend on its children; a gate checked it is equal at six viewports.

Before / after

Cost and caveats

  • The goal count did not separate. Frames over 50 ms in the window went 3, 1, 2, 2 → 1, 1, 1, 1. The ranges touch at 1, so by the block's rule that is no separation at n = 4, and it is threshold-sensitive (see case 9). It landed as a "does less work" fix, not as a 50 ms win.
  • One long frame is left at y ~1750 in every run (51-52 ms, down from 61-63). It is a different cause: case 3.
  • Serve it, don't inject it. Injected after load, the same rules left 34-47 big layouts near the top; served in the stylesheet they left none. Why is UNRESOLVED.
  • A Simulator-only look difference. After a swipe some deck photos were painted at a different resampling quality (the new build as sharp or sharper). WebKit's image quality controller paints scaled bitmaps at low quality while a bitmap's drawn size changes CONFIRMED as code (ImageQualityController.cpp 46, 196-228); that it explains these shots is OBSERVED. The difference stayed inside the project's look-alike limits.

Case 03ScriptStyleLayoutPaintComposite

Never add the first wheel listener mid-scroll

Build g0.0k · finding F-360

Symptom

On every drag toward the end of the page, one frame at y ~1750 ran long: 61-63 ms on the phone before case 2, 51-52 ms after it. Always the same place.

How we measured

  • Simulator robot-finger drags with Timeline, a patched addEventListener log and a MutationObserver, so each long frame could be matched to what the page did in it.
  • Ablation arms: move each of the frame's three jobs elsewhere, one at a time.
  • iPhone block P-173 (driver G, 4 runs per arm): the longest frame between y 1650 and 1850, called X.

Root cause

At that y an IntersectionObserver with a 200 % root margin sees the end-of-page section come within reach. Its callback did three things in one frame: gave 21 images their src, lifted inert on the hidden panel, and added three window listeners, among them a non-passive wheel listener.

Arm (Simulator, 3 loads each)That frameIts layout + style
As built102.5-117.7 ms158-171 ms
Wheel listener added once at load instead33.5-59.0 ms48-52 ms
Image src or inert moved out130-154 ms175-227 ms
Listeners added later, at y ~3990a new 82-117 ms frame there

The wheel listener alone carried the spike, and moving it only moved the spike. The source says why. The first window wheel listener changes the root style's event-listener region types, and Document::invalidateEventListenerRegions() then schedules a full style rebuild CONFIRMED (WebKit main, LocalDOMWindow.cpp 2150-2172, Document.cpp 6648-6663). The types are inherited, so every element's style is involved, and passive listeners change the set too CONFIRMED (StyleAdjuster.cpp 227-262). Touch listeners take an early return unless touch event regions are on CONFIRMED (Document.cpp 12723-12730); whether shipping iOS Safari turns them on is UNRESOLVED, and in our data the touch pair was cheap OBSERVED.

Fix

Register global listeners once, at load or teardown, and switch their behaviour with a flag. In g0.0k the phone path goes further: it never adds a wheel listener at all (phones only need passive touch listeners, registered at setup).

let armed = false;
addEventListener('wheel', e => { if (armed) onWheelNearEnd(e); },
                 { passive: false, capture: true });   // once, at load

new IntersectionObserver(([entry]) => {
  armed = entry.isIntersecting;                        // no listener add here
}, { rootMargin: '200% 0px' }).observe(endSection);

Before / after

Cost and caveats

  • A non-passive wheel listener present from load makes every wheel and trackpad scroll wait for the main thread. So scope it: in our build, desktops and reduced-motion users keep the listener, added once at mount, and phones never get one.
  • The rebuild still happens once at load. That is a load-time cost, paid during hydration, before anyone scrolls.
  • About 5-8 ms of layout + style still runs at the crossing in the Simulator (background p90 1.5 ms). It no longer makes a long frame.

Case 04ScriptStyleLayoutPaintComposite

Keep the glass steady, fade only its colour

PR-040 "steady glass" end of page · build g0.0k

Symptom

The menu bar at the end of the page is frosted glass: backdrop-filter: blur(20px) over a light tint. As the bar grows into the dark menu panel, the original page blurs less and darkens. In our compositor version (case 1) the glass vanished and came back while the finger moved near the start of the grow.

How we measured

Simulator, robot finger wiggling around the start of the grow (6 short strokes), a screenshot after each move, and a sharpness score of the glass region: 0.02-0.09 when frosted, up to 1.87 when the glass is missing.

Root cause

With the blur radius on a scroll-driven animation, the glass was missing in 12 of 33 shots OBSERVED, cause unknown. The earlier script version avoided that by writing blur(20px × (1 − m)) from script at each step, which brings back per-frame style writes. And a changing blur value is expensive by itself: WebKit repaints a filtered element's contents on frames where the filter value changes OBSERVED (at rest, a constant blur(0px) cost nothing measurable), while Chrome never runs blur animations on the compositor CONFIRMED (Blink compositor_animations.cc, failure reason 4096).

Fix

Don't animate the blur. Keep it at 20 px for the whole grow and put the darkening on a separate layer whose opacity follows the morph. The original page mixes the tint from a 10 % white toward a dark navy; a dark layer at opacity m over the light tint gives the same path.

.bar { backdrop-filter: blur(20px); background: #ffffff1a; isolation: isolate; }  /* set once */
.bar::before {                                    /* the dark fill, under the content */
  content: ""; position: absolute; inset: 0; z-index: -1; background: #131922;
  animation: darken linear both;
  animation-timeline: --menu;
}
@keyframes darken { from { opacity: 0 } to { opacity: .9999 } }  /* stay off 1: see below */

The .9999 end is deliberate: in WebKit, an opacity change that crosses 1 is a Layout-level style difference, not a repaint-only one CONFIRMED (StyleDifference.cpp 192-209, tag 7624.4.5).

Before / after

On the phone (P-173, driver G, 4 runs per arm) frames over 50 ms at the end were 0 in every run of both builds, and the share of frames over 34 ms stayed in the same range (0.13-0.27 % before, 0.17-0.30 % after).

Cost and caveats

  • It changes the look. The glass no longer clears as the menu opens. That made it a proposal with live A and B pages; the user accepted it (PR-040).
  • Style work went up, as case 1 predicts: style recalcs per frame 1.00 → 1.43 in the Simulator, and 45-49 style records of 5 ms or more per phone run at the end, against 0-1 before. None of them made a frame over 50 ms.
  • Memory at rest went up with the menu closed: 46 layers / 77.2 MB → 53 / 103.6 MB, because the menu's layers are built ahead of the first open.

Case 05ScriptStyleLayoutPaintComposite

Give a ticking clock its own small layer

Build g0.0i · two CSS rules, Safari only

Symptom

Nothing the user could point at. The open menu holds a second countdown, and a layer census in the Simulator showed it repainting a big layer once a second. This case is a "does less work" fix: fewer bytes moved per frame, no frame-time claim.

How we measured

Simulator layer census (layers, backing memory) and paint counts per layer over one menu open, stepped frame by frame.

Root cause

The open menu's centre is its own WebKit layer: 406x389 CSS px at device pixel ratio 3, a 5.7 MB backing store. The clock's digit cells paint into it without a layer of their own. Each roll (about 0.4 s, once a second) changes their transform every frame, and WebKit re-displays the centre: 196 paints of that layer over one open.

The invalidated rectangle is already small. But each display of a layer swaps its buffers, marks the new one non-volatile and copies the previously painted area forward CONFIRMED (WebKit main 6d3243c9, ImageBufferSet.cpp 42-75, 103-148), and the copy covers the whole layer after a 200 ms volatility timer fires between rolls CONFIRMED (RemoteLayerBackingStoreCollection.mm 45, 124-143). Whether Core Animation then re-uploads the whole surface is UNRESOLVED.

Fix

.menu-centre .clock { isolation: isolate; }                 /* always */
.menu[data-scene="active"] .menu-centre .clock {
  will-change: transform;                                    /* only while shown */
}

The wrapper becomes a 1.2 MB layer only while the menu is open. The constant isolation matters: toggling will-change on a z-index: auto element flips its used z-index between auto and 0, and WebKit answers that with a Layout, not a recomposite CONFIRMED (StyleAdjuster.cpp 391-410, StyleDifference.cpp 428-429, WebKit main f9dcd0ee).

Before / after

On the phone (P-170b, driver G, 2 runs per arm) the first open frame was 16.5 ms in both builds, the open median 17 ms in both, and 0 frames over 50 ms in both: no worse.

Cost and caveats

  • One more layer and 1.2 MB while the menu is open (53 / 77.3 MB → 54 / 78.5 MB). With the menu closed, nothing changes.
  • Chrome drew the composited digits 1 CSS px higher OBSERVED, so the rules apply only in Safari, keyed on the page's own 'GestureEvent' in window test.
  • Mid-open, the clock's glyph edges antialias slightly differently in the Simulator; at rest the frames are identical.
  • The phone check ran with 2 runs per arm because the first block (3 per arm) was voided by its heat check (49.4 fps at 43 °C; see case 8).

Case 06ScriptStyleLayoutPaintComposite

Hold a hidden animation as a still picture

PR-039 "keep-phase" · build g0.0h

Symptom

None visible. The closed menu holds four columns of photos that drift up and down when it is open. Closed, their animation was paused, and the Simulator's census still counted their layers and graphics memory at the top of the page, far from the menu.

How we measured

Simulator layer census at the top of the page, and a phase check: how far the columns jump when the menu re-opens (one frame of their motion is 0.14-0.16 px).

Root cause

A paused keyframe effect on transform keeps its element composited; a static 2D transform does not CONFIRMED (WebKit main 94a902b2, RenderLayerCompositor.cpp 3902-3910 and 3949-3951). So animation-play-state: paused saves the ticks but keeps the layers, and anything that overlaps them may need layers too.

Fix

When the menu closes, freeze each column at its current frame as a plain transform and drop the animation. When it opens, remove the transform and restart the animation at the same phase with a negative delay.

function hold(track) {
  const [anim] = track.getAnimations();
  track.dataset.phase = anim.currentTime % anim.effect.getTiming().duration;
  track.style.transform = getComputedStyle(track).transform;  // still picture
  track.style.animation = 'none';                             // no effect, no layer
}
function resume(track) {
  track.style.transform = '';
  track.style.animation = '';
  track.style.animationDelay = `-${track.dataset.phase}ms`;   // same phase
}

Before / after

Cost and caveats

  • One computed-style read per column at the moment the menu closes. It runs at a still moment, never in a scroll frame.
  • No frame-time gain is claimed. This landed on fewer layers and less memory, plus a phone check that nothing got worse.

Case 07ScriptStyleLayoutPaintComposite

Skip a time-based reveal when the user flings

PR-041 "instant" · build g0.0l, the current best

Symptom

A fast fling down from the top lands on the people section, and its profile deck "blinks": it arrives white, then blurred, then turns sharp. The original site does it too.

How we measured

  • iPhone, driver G flicks (300 px in 220 ms from the top), Timeline on, plus screen-capture frame numbers.
  • Simulator flicks with a sharpness score per screenshot; Chrome screencast of a synthetic fling.
  • Then block P-174 (driver G, 4 runs per arm) with a page log that counts frames where the deck is in view while its blur is still running.

Root cause

This was not a stall. The screen capture showed 0 frame gaps over 34 ms during the fling OBSERVED. The page drew every frame on time; it drew the wrong picture. The card holding the deck is hidden (opacity: 0, blur(14px), 48 px lower) until a scroll threshold, and then plays a time-based fade. The trigger, in Fastwork's code:

// Fastwork bundle, prettified baseline JS line 11310 (quoted for attribution)
z(y, e.matches || i / r >= 0.72, !0)

That sets the reveal once the hero is 72 % scrolled; the fade then runs 0.7-1.6 s. A fling covers the distance from that threshold to the deck in about 0.5 s, so the deck arrives mid-fade. Its eight lazy photos also load during the fling, behind the blur OBSERVED. Every frame-time metric in this study was blind to it.

Fix

Measure scroll speed at the moment the threshold flips. Above 0.8 px/ms (phone flings measured 1.04-2.89), take the end state at once; slower scrolls keep the original fade. On touch screens, load and decode the deck's photos after the page's load event, so a sharp card is also a complete one.

let lastY = scrollY, lastT = performance.now();
function onScrollFrame(now) {                    // already runs once per rAF while scrolling
  const speed = Math.abs(scrollY - lastY) / (now - lastT);   // px per ms
  lastY = scrollY; lastT = now;
  if (!shown && progress() >= 0.72) {
    if (speed >= 0.8) section.dataset.reveal = 'instant';
    section.classList.add('is-visible');
    setTimeout(() => delete section.dataset.reveal, 400);
    shown = true;
  }
}
/* CSS */
[data-reveal="instant"] .card { transition: none; }

Before / after

Cost and caveats

  • The reveal frame got heavier. The decoded photos now paint and upload in the frame that shows the card: Paint +6-9 ms and Composite +6-12 ms, that frame 44-60 ms instead of 35-47 ms OBSERVED. Frames over 50 ms per flick went 0, 0, 0, 0 → 1, 1, 0, 1, inside the block's no-worse limit of +2. A next step would let the hidden card paint ahead so the reveal only composites.
  • Decoding ahead changed resampling in Chrome desktop by up to 0.8 % of pixels, so the preload is limited to touch screens.
  • A scroll-driven reveal was considered and not proposed. Safari 26 supports it CONFIRMED (ScrollDrivenAnimationsEnabled stable from the safari-7622 branch), but a page stopped inside the range would show a half-blurred card, and whether 26.6.1 runs it threaded is UNRESOLVED.
  • It changes the look of fast scrolls, so it went to the user as a proposal with A and B pages; Part 3 follows that path from the user's report to the phone check.

Case 08Around the pipeline: the device

Treat heat as a variable

research/phone-heat (P-068) · research/serious-heat

Symptom

The phone got warm during test blocks, and results drifted with it. The same build measured smooth at the start of an hour and laggy at the end. Later, the user asked for the page to stay smooth in the phone's hot "Serious" thermal state.

How we measured

One identical 6-minute routine (3 minutes untouched at the top, then scripted window runs) on four pages, in two sessions, with the battery held at 80 % on the cable. The score is the battery temperature slope, corrected to a 37 °C start.

  • Floor: a static page as tall as Fastwork's, with no images, fonts, scripts or animation.
  • apple.com: a heavy product page, loaded live by the phone as an outside reference.
  • Fastwork, original, and Fastwork with the fixes of that day (before the countdown fix).

What we found

The page's own always-on work heated the phone: above the floor, the original Fastwork page warmed it 5 to 5.5 times as fast as apple.com did OBSERVED. Then we looked at what heat does to the page:

  • The GPU side slows, the CPU does not. Under induced Serious a CPU loop ran at the same speed, and a sustained GPU animation ran about 25-35 % slower OBSERVED (n = 3, cause unknown). So "move more to the GPU" helps only work that waits on the main thread.
  • Timers land on a 30 ms grid. WebKit's thermal mitigation aligns DOM timers CONFIRMED (DOMTimer.h:54). A repeating timer re-arms from when it actually fired, so setInterval(f, 1000) fires every 1020 ms and a once-a-second clock skips a second about every 50 s CONFIRMED (WebKit main bdc535f8, Timer.cpp 502-520, DOMTimer.cpp 436-448), and the phone showed 1020 ms gaps OBSERVED.
  • rAF is not halved by default; that needs the aggressive mitigation preference, off by default since WebKit a8c0b8f CONFIRMED. Heat and Low Power Mode do turn off the high frame rate Core Animation could otherwise grant CONFIRMED (Apple, "Optimizing iPhone and iPad apps to support ProMotion displays").
  • Most heat lag sat right after load: 17 % of moving frames slow in the first 8.5 s, 7 % from 8.5 to 20 s, 1 % after OBSERVED (8 robot-finger runs).

What we changed in the method

  • Every phone block starts with one uncounted warm-up run per build's port, because a cold first run is slow.
  • A sentinel: the control build must still reach 58 fps at the bottom and 44 fps while scrolling. A failure voids every run since the last passing one. Idle fps is no heat check: it stays at 60 while the phone throttles.
  • Phone checks now run in a fixed hot state, Serious induced by a tool, so every run starts equally warm. Results from different heat profiles are never pooled.
  • Under real heat, the phone cools between blocks until the battery is 0.5 °C under the last passing sentinel's temperature. Part 3 shows where these checks sit in a block.

Caveats

  • Battery temperature lags the chip. It is a cooling cue, never a validity check; the sentinel decides.
  • One phone, one day, apple.com live and not frozen. The system power readings agreed in direction, but their units are UNRESOLVED, so no watts are claimed.

Case 09Around the pipeline: the reading

Read a result: ticks, twins, sentinels, A/A

research/architecture/measurement-protocol-v2.md · research/cpu-throttle-calibration

Symptom

Early on, results flipped between runs, a Chrome win didn't show on the phone, and a 49 ms frame and a 51 ms frame got opposite verdicts. These are the rules that made a number mean the same thing twice.

Calibrate the fast tool to the device

The iPhone is not slow at JavaScript: on a CPU microbenchmark it matched this Mac's Chrome at 1x (261 vs 255 ms). Its page still janks, because WebKit's costs differ and every miss costs a whole 16.7 ms frame. So we matched the symptom instead. Under the same scripted scroll:

Count in the device's own units

Chrome on a 120 Hz screen stamps frames on 8.33 ms ticks, so Chrome counts use ticks (the ruler at the top). Safari stamps the start of each rendering update at 1 ms resolution CONFIRMED (Document.cpp l.8959, Page.cpp 2424-2428), and in 198,349 phone gaps the long ones spread smoothly with no peaks at 33.3 or 50 ms OBSERVED. So the phone uses plain ms thresholds. Safari asks for 60 Hz page updates only as a hint CONFIRMED (pref PreferPageRenderingUpdatesNear60FPSEnabled), and finger runs show stretches of ~80 Hz, so frame counts from touch runs don't compare with scripted runs; ms thresholds do.

Know your noise floor

  • A/A first. Measure the baseline against itself. Screenshot diffs of 0-0.4 % were the countdown's and carousels' own phase, not a change. A Chrome verdict is "better" only when the two ranges don't overlap over at least 3 runs.
  • Host load moves the numbers. On the unchanged page, frames over 20 ms were ~66 at a load average under 6 and 96-103 at 6-15. Never compare a busy-host A/B with a quiet-host A/A.
  • Small n, exact tests. A phone block is 4 runs per arm in C V V C C V V C order; the strongest one-sided result 4 against 4 can give is p = 1/70. That is why several cases above landed on "does less work, and no worse" rather than on a 50 ms win.
  • The driver bounds the claim. A scripted scroll never runs touch handlers: making a touchmove listener passive measured flat (52.7 vs 52.5 fps). Touch, bounce and toolbar effects need the robot finger or a person.
  • Check the logger can fire. A MutationObserver watching the wrong container reported 0 added notes while 11 were added. Before trusting a zero, make the counter count something.

Case 10Around the pipeline: the reading

Don't show frame timing in a GIF

research/team-article/capture/medium-visuals.mjs

Symptom

For the Medium copy of Part 1, the page's live pacing animation ("smooth" next to "one late frame") had to become an animated GIF. At a typical GIF rate of 12-15 fps the difference vanishes: every frame is slow, so the late ones no longer stand out.

Root cause

A GIF stores each frame's delay in hundredths of a second CONFIRMED (GIF89a specification §23, "Delay Time"). And browsers treat very short delays as long ones: WebKit plays any delay under 11 ms as 100 ms CONFIRMED (ImageDecoderCG.cpp 591-596, WebKit main e6eb9ebd), and Chromium does the same for 10 ms or less CONFIRMED (deferred_image_decoder.cc 301-306, Chromium main 6140d183). Both comments cite Firefox's behaviour. So the fastest rate that plays the same everywhere is 20 ms per frame, 50 fps, and 16.7 ms can't be written at all.

Fix

Draw the illustration on a virtual clock (the page's requestAnimationFrame and performance.now replaced before it runs), step it at 20 ms per GIF frame, and hold each late frame for its rounded length. For recorded before/after clips at 30 fps, alternate delays of 30, 30 and 40 ms so three frames take exactly 100 ms and the clock keeps time.

const delayCs = ms => Math.max(2, Math.round(ms / 10));  // GIF units; 2 = 20 ms floor
delayCs(16.7)  // 2  → plays 20 ms: the smooth lane runs at 50 fps
delayCs(58)    // 6  → plays 60 ms: the late frame stays visibly late

Caveats

  • A GIF is a schematic of pacing, not a recording. It says so in its caption.
  • In an HTML page, draw pacing live (a canvas on requestAnimationFrame) or use video.

What carried over

Eight rules we now check first

  1. Find the stage before the fix: script, style, layout, paint or composite. A Simulator call stack tells a forced read from the engine's own work.
  2. Move per-frame motion to transform, opacity or filter on a scroll or time timeline, and expect the style pass to stay.
  3. Remove every layout read in a moving frame. A removed read moves the forced layout to the next reader until none are left.
  4. Watch for boxes that size themselves from their own layout (aspect-ratio, percent heights) inside anything sticky.
  5. Add global listeners at load; gate them with a flag.
  6. Don't animate a blur; animate what sits over it.
  7. Give small, frequently changing content its own small layer, and keep its stacking context constant.
  8. Ask what a frame-time metric can't see: a reveal that plays on time can still look broken.
