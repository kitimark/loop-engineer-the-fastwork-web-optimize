## Question

On v9.1d in WebKit, does a deck whose height needs no content measurement remove the deck's per-frame Layout cost
during a scripted swipe, when measured with enough control frames and several runs per arm?
- A3 is that height plus size and layout containment; A4 is the container-query form; R3 is A3 without containment.
- Is that effect stable across runs, or does it switch between levels the way P-143's single runs did?
- The N1 behaviour rules and pixels T0 from P-143 rev 1.1 are kept.

## What P-143 showed that this card is built on (all OBSERVED in our setup, cause unknown)

1. **C band frames per swipe.**
   - 7 C swipes gave 46-66 frames in the deck band: DRY1 66; S1 46, 59, 61; S2 64, 46, 56.
   - Arm swipes gave 104-162.
   - A C run draws only 90-110 RenderingFrames for 260 scroll steps.
   - So one C swipe sits at MIN_N 60 by construction.
2. **Three levels.** Layout ms per band frame landed on three levels: C about 38, a middle level about 25, a low level
   about 0.43.
   - Layout records per frame stayed at 2.74-2.90 in every run.
   - The same arm landed on different levels in different holds: A3 0.43 / 25.6; R3 0.44 / 25.4; A4 0.43 / 0.43.
   - The low level came with 259-260 frames drawn, the middle level with 145-152.
3. **Strict + 844 px (P-143's PC)** read 0.67 and 0.64: the middle level, twice. It is not a control that LOCATES on this
   driver.
4. **First step of a session.** The first step of every session read the deck top 48 px lower than every later step.

## Design changes (each justified from the numbers above)

### D1: pooled swipes per run, so control runs have enough band frames by construction

- `sim-swipe-p146.mjs` repeats the whole P-143 step (cold open, 4 s settle, arm CSS, Timeline, one swipe) inside one run.
  It stops when the pooled band frame count reaches **POOL_N = 120**, or after **POOL_MAX = 4** swipes.
- All swipes' frames go into one record, and L is the median over the pooled band frames.
- Why 120 and 4:
  - the worst C swipe seen had 46 band frames, so 3 swipes give at least 138;
  - the best C swipe gave 66, so 2 swipes give 132;
  - arm swipes give at least 104, so arms need at most 2.
- **MIN_N becomes 100 for a pooled run.** A run stopped early by the budget with fewer than 100 frames is LOW-N, as
  before.
- Every swipe of a run must read the same deck top and docH, within 2 px. Otherwise the run is **POOL-MISMATCH**, which
  counts as not OK.
- Alternative not taken: a band defined by scroll position, with a minimum taken over pooled swipes. It needs a frame
  match by position across swipes. P-143's own band (`deck.top - innerHeight < y < deck.bottom`) is kept unchanged, so
  results stay comparable with T-194 and P-143.

### D2: a warm-up step, so the first-step 48 px offset never enters a scored run

- Every hold starts with `W:0`: the base, one swipe, no pooling.
- The scorer drops every `<arm>:0` step when it loads a hold, so `W:0` is never scored.

### D3: a positive control that should LOCATE on this driver, and several runs per arm

- **PC2** (`arms/pc2-cv-hidden.css`):
  - A3's content-free height: `height: 0; padding-block: 0 calc(100% * 764 / 353); align-items: flex-start`;
  - plus `content-visibility: hidden`.
- Why it should LOCATE: `content-visibility: hidden` skips the element's contents and applies size, layout, style and
  paint containment. CONFIRMED by spec: CSS Containment 2 §4 (the normative sentence for `content-visibility: hidden`; rev 1.1 N7), "the element skips its
  contents".
  - The deck subtree is then not laid out at all.
  - The deck keeps the base height (A3's padding), so docH and the band stay the base's.
  - It blanks the deck. That is fine for a control, which is never a candidate.
- **What LOCATES means for PC2.**
  - PC2 LOCATES in a hold (ratio <= 0.30): removing the deck's content work removes the per-frame Layout cost. The C
    level (about 38 ms) is then deck work, and arm ratios in that hold are read.
  - PC2 does not LOCATE: some per-frame Layout cost stays with the deck's contents skipped. The hold is
    **CONTROL-FAILED** and no arm is read in it.
  - If PC2 sits at the middle level (about 0.65): the card reports that, in our setup, about 25 ms per band frame is not
    deck-subtree work. That is OBSERVED; P-146 makes no attribution of the middle level beyond that.
- **Why not P-143's strict + 844 px as the control.**
  - It read the middle level in 2 of 2 runs (0.67, 0.64), so it would fail as a control on this driver.
  - Its fixed 844 px is 0.078 px shorter than the shells' ratio height (844.078). Whether that difference matters is
    UNRESOLVED. A decisive local check would be the same arm with `height: calc(100cqi * 764 / 353)`; it is not part of
    this card.
  - It is not run in P-146: S844 is in the driver's arm table but in no hold.
- **Several runs per arm.** Each arm gets 3 runs, one in each of 3 holds, in rotated positions.
  - The arm's call is on the **median** of its valid run ratios over all readable holds, with at least 2 valid runs.
  - Each run's level is reported: low <= 0.30, high > 0.50.
  - **BIMODAL** is flagged when an arm has runs at both levels.

## Holds (registered; nothing runs before the signature)

Three normal exclusive chrome-measure holds, each `--max-seconds 600`, in P-133's form: a cold Simulator session each,
FIFO, in the background, nobody moved, DEFERRED during a phone block.

- H1: `W:0 C:1 PC2:1 A3:1 C:2 R3:1 A4:1 C:3`
- H2: `W:0 C:4 A4:2 R3:2 C:5 A3:2 PC2:2 C:6`
- H3: `W:0 C:7 R3:3 PC2:3 C:8 A4:3 A3:3 C:9`

```sh
node tools/lock.mjs run chrome-measure --max-seconds 600 --owner fix-deck-contain --doing "P-146 Simulator hold H1" -- \
  node tools/sim.mjs session --owner fix-deck-contain -- node fixes/deck-contain/sim-swipe-p146.mjs H1 W:0 C:1 PC2:1 A3:1 C:2 R3:1 A4:1 C:3
```

**Budget** (disclosed basis: DRY1 C:0 26.5 s and A3:0 22.8 s per swipe step; S1/S2 per-step 17.5-27.3 s):
- Worst case per hold, driver side: W 28 s + 3 C x 3 swipes x 28 s + 4 arms x 2 swipes x 24 s = 28 + 252 + 192 = 472 s.
  That is under `SB_BUDGET_S` 500.
- Hold overhead outside the driver (boot, settle, shutdown) was 61-76 s in DRY1, S1 and S2 (holds.log 111/230/236 s minus step sums 49/154/163 s; rev 1.1 N4), so a hold totals at most about 576 s, inside 600 s.
- The budget is checked per swipe:
  - a step starts only if one swipe fits;
  - pooling stops when the next swipe would not fit (`poolStopped: budget`);
  - such a run may be LOW-N.

**Then**, in this order:
1. Chrome counts C1: one shared probe slot, `chrome-swipe.mjs C1 <url> C:1 A3:1 A4:1 R3:1 C:2 A3:2 R3:2 C:3`.
2. P15/P16 (N1) in Chrome and the Simulator.
3. `px-chrome`, then `px-sim`.

All of these use the commands and rules of P-143 rev 1.1, unchanged.

## Rules (frozen before data; scorer `score-p146.mjs`, self-test `selftest-p146.mjs`)

P-143 rev 1.1's rules hold except where listed here:

1. **Hold replication** (P-143 rule 1): every C run OK (pooled n >= 100, applied, not SHORT, not POOL-MISMATCH), at least
   2 C runs, and every inner C's A/A ratio in [0.80, 1.25]. Otherwise the hold is NOT-REPRODUCED.
2. **VOID** at drift > 30 % (unchanged). **VOID-HOST** at load1 > 200 (unchanged; the folder is renamed `<hold>-void1`
   and the hold re-run once).
3. **CONTROL-FAILED**: PC2 does not LOCATE in that hold. Its arms are not read.
4. **Arm call** over all readable holds: the median of the valid run ratios. LOCATES <= 0.30, PARTIAL <= 0.70, NONE
   above. INSUFFICIENT with fewer than 2 valid runs. BIMODAL is reported beside the call.
5. **GEOMETRY** (unchanged): docH > 2 px or deck height > 0.5 px against a neighbouring C.
6. **Rules carried from P-143 rev 1.1:**
   - pixels T0/T1/FAIL (`judge`, N6);
   - P15/P16 and the landing rule (N1);
   - HOLD-EXISTS (N4; holds under `out/deck-contain/sim146/`);
   - Chrome counts rules (N5).
7. **Precedence** (as P-143 rule 8, plus): fewer than 2 readable holds makes every arm call INSUFFICIENT. A CONTROL-FAILED
   hold is reported with its PC2 level.

## Decision (registered before data)

- **Build candidates.** Only an arm that LOCATES and is **not BIMODAL**, passes pixels and passes P15 and P16. The order
  is R3, then A3, then A4, as in P-143 rev 1.1. An arm failing P16 goes to the user as a proposal with Try-it pages (the
  N1 ruling).
- **A LOCATES arm that is BIMODAL** is not built from this card. Its low/high split goes to the lead as a finding: the
  arm sometimes removes the cost and sometimes does not.
- **PC2 CONTROL-FAILED in every hold that passes rule 1:** P-146 reads "deck-subtree layout is not the whole per-frame cost on
  this driver". No build, and the deck-contain topic goes to the lead.
- **Rule 1 fails in 2 or more holds:** NOT REPRODUCED. No build.

## Rev 1.1 addendum: the read's notes N1-N7 (lead rulings; registered before any P-146 data)

Rev 1 was read by ops-reader-P143r-P146 at 6fd4af77: PASS WITH NOTES N1-N7. The lead accepted N1 and ruled N2-N7 as
the reader wrote them.

**N1, the budget-drop branch.**
- Rev 1's driver logged `est.toFixed(0)` in its drop branch, after `est` had been renamed. That would have thrown and
  ended the hold with no record for its later steps.
- The drop is now a pure, exported function `budgetDrop()`. The self-test exercises it: both the null case and the drop
  case, including its log line.
- **New rule 1a: a hold lacking a record for any registered step (other than `W:0`) is NOT-REPRODUCED.**
  - The driver writes `hold.json` with the registered steps at the hold's start.
  - The scorer compares the records against it, and a hold without `hold.json` is NOT-REPRODUCED too.
  - A budget-dropped step has a record (`dropped: budget`), so it is not "missing". It counts as a not-OK run: a dropped C
    fails rule 1; a dropped arm has one run fewer.
  - Self-test: a hold cut after R3:1, a missing manifest, a dropped arm.

**N2, precedence per prediction.**
- A P1 miss makes P2-P6 insufficient.
- P2 is insufficient when no hold passes rule 1.
- P-143's "PARTIAL is a miss" clause covers P3 and P4 only; P5 passes on PARTIAL.
- P3-P5 are scored on the median call whatever BIMODAL says. GEOMETRY is a miss; INSUFFICIENT is insufficient.
- P6 is a miss only when A3, A4 and R3 all have at least 2 valid runs and none is BIMODAL; otherwise it is insufficient.
- Rule 4's 2-run minimum overrides P-143 rule 8's "an arm left with one run is called on it".
- P7 and P8 are scored over all scored holds.
- P9-P16 follow P-143 rev 1.1 N5 and are insufficient when not run.

**N3, levels within a pooled run.**
- A pooled run that mixes levels reads at the level with more band frames. A low-level swipe gives about 162 frames, a
  middle-level one about 105, so a middle swipe followed by a low one reads low.
- BIMODAL is therefore per run, not per swipe.
- The driver now tags every frame with its swipe index. The scorer reports per-swipe band n and median Layout ms
  (`swipeL`) for every run, as descriptive numbers only; no rule reads them.

**N4, budget basis.**
- Hold overhead outside the driver was 61-76 s, not "capped at 60". Worst case per hold is 472 s driver + 76 s overhead,
  about 548 s; with margin, about 576 s, inside the 600 s hold.

**N5, decision wording.** The decision line now reads "deck-subtree layout is not the whole per-frame cost".

**N6, W:0 and VOID-HOST.**
- The loader drops `:0` rows, so a VOID-HOST at `W:0` is caught only by the driver's exit 28 and the folder rule. The
  folder is renamed `<hold>-void1` and the hold is re-run once.
- A W:0 record is never read for anything else.

**N7, citation.** CSS Containment 2 §4, the normative sentence for `content-visibility: hidden`, instead of §4.1.

**Recorded, no rule (from the P-143 result read).**
- The Simulator settle state (`SIM_QUIET`) and the display state at hold start (the lock's I-033 warning) are copied
  from each hold's log into the results and reported.
- No rule depends on either. P-143's three holds all started with the display off, and S1 never settled.
