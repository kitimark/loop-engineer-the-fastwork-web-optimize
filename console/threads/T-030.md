## #2 · lead · 2026-10-02T23:01:03.348Z

Good idea, I'm starting it now (agent de-gpu). Short version of what it covers: browsers can run some animations on the GPU compositor without the main thread: mainly transform and opacity (and in Chrome also filter, plus a few newer cases). Animating other properties (top/left, width/height, margins, background-position, box-shadow, clip-path in some engines) makes the main thread lay out or repaint every frame. That is exactly the kind of work behind the slow frames we measured. The research will: (1) collect what Chrome and Safari/WebKit actually put on the GPU, with references to their docs and source, because the two engines differ; (2) go through every animation on the Fastwork page and mark which ones animate a 'slow' property and could be rewritten as transform/opacity with a pixel-identical look; (3) note the costs: every GPU layer uses memory, and too many layers (like the countdown's 80) made WebKit slower before, so 'put everything on the GPU' is not free. Several of our fixes already did this (the countdown faces, the carousel), so it will also say which ideas are already used. I'll post the list here when it's ready.

## #7 · lead · 2026-10-03T00:08:00.184Z

All de-gpu findings (full report: research/gpu-props/README.md). CONFIRMED = checked against Chrome/WebKit source, docs or the WebKit blog; OBSERVED = our own measurement only (single runs).

A. What the GPU can animate by itself (no main-thread work per frame), CONFIRMED
1. Both Chrome and Safari: transform (also translate/scale/rotate), opacity, filter, backdrop-filter.
2. Exceptions: Chrome keeps blur/drop-shadow animations on the main thread. Safari keeps steps() and linear(...) easings on the main thread (normal 'linear' and cubic-bezier are fine).
3. Chrome only: background-color and clip-path also run on the GPU. Safari runs them on the main thread.
4. Always main thread in both: background-position, mask-position, width/height/gap/margins, stroke-dashoffset, colours, custom properties (--x), SMIL SVG animations, and anything JavaScript writes every frame.
5. Mixed animations: in Chrome one slow property drags the whole animation to the main thread; Safari keeps the fast part on the GPU.
6. Safari 26.4+ runs scroll-linked CSS animations (animation-timeline: scroll()/view()) on its scroll thread, even with steps()/linear() easings (WebKit blog 17862 + source). Your phone has 26.6.1.
7. Safari detail: a GPU layer that leaves its clip box loses its picture and must repaint when it comes back; a running GPU animation prevents that.

B. This page
8. Most of the page's CSS animations already use GPU properties (scroll cue, vinyl, marquees, card entries, carousel on the best build).
9. Not GPU today: countdown digits (JavaScript every frame), the accent word drawing, the blinking carets/boil (GPU in Chrome, main thread in Safari because of steps()), the 4 "sweep" titles, the small glint on the 'secure' picture (SMIL), card entry blurs (Chrome only), a one-time mask wipe on the nav button at load, and some layout transitions (gap, row height, nav width).
10. About half of the platform-section animation CSS never runs: its HTML isn't on the page (dead CSS, ignored).
11. At rest on the best build, the page still draws every frame because of: the countdown (top), typing and count-up effects (middle), and in the platform section only the sweep titles + the glint. Pausing those two makes that part fully idle in Chrome (120 frames per 2 s down to 5).

C. Your last finger run on the best build ('optimize 2'), OBSERVED, one run each
12. The middle and bottom of the page are clean now (17 slow frames between 1000-5000 px vs 45 in the original; 1 vs 21 below 5000 px).
13. What you still feel: (a) the first ~1000 px, where the hero fades out and the next section comes in: 63 of the 81 slow moving frames; (b) the menu panel at the end while your finger holds it there: 91 slow frames, median frame 20 ms (just under 60 fps).
14. The Safari toolbar showing/hiding is NOT the main cause: mid-page toolbar changes ran at 13-18 ms frames. Safari does re-lay out fixed/sticky boxes and anything sized with vh/dvh on each toolbar frame (CONFIRMED in WebKit source), but on this page it's small.
15. One exception: scrolling back up from the end while the menu panel closes gave 84/66/42 ms frames; the panel's height uses 'dvh', so it re-lays out on every toolbar frame (one run; fix-nav-morph is taking this).

D. Ideas checked for the countdown
16. Pre-drawn digit strip (one image strip 0-9 per digit that only slides): identical by construction, no digit repaints at all, 8 layers per clock instead of 24. Cost: ~2 MB GPU memory per clock. -> fix-cd-strip (started).
17. Countdown roll as a GPU animation: removes the JavaScript too, but its motion can differ from the original by up to ~0.08 px per frame. Not pixel-identical -> parked, your call.
18. steps() easing: rejected (changes the look, and Safari runs it on the main thread anyway).
19. 'contain' / content-visibility on the clock: little value.

E. Ranked fixes
F1 cd-strip (started, #1): countdown digits as strips; helps the top and the menu pin; identical.
F2 hero-exit-threaded (started, #2): hero fade-out as a scroll-linked CSS animation on Safari's scroll thread; helps the top ~1000 px; identical as a function of scroll position (measured on the phone earlier); first it must explain an extra ~11 ms frame an earlier version caused at the hero's end.

I1 glint-ca and I2 sweep-exact (parked): make the platform part fully idle; saves battery/heat, not lag (almost no slow frames left there).

F. Not recommended

## #15 · user · 2026-10-03T06:45:12.118Z

Explain "glint-ca, sweep-exact (battery/heat only)" detail ? why it cause battery heat but it not impact the animation performance, doesn't it ?

## #16 · lead · 2026-10-03T06:45:34.165Z

Good question. Short answer: they cost energy every frame, but not enough to make a frame late, so you don't see a stutter from them. Their effect on smoothness is indirect (heat), and we haven't measured that part.

What they do today:
- glint-ca: the small light glint on the "secure" picture is an old-style SVG animation. Safari redraws that picture area on every frame (60 times a second) while it is on screen, on the main thread.
- sweep-exact: the 4 colour "sweep" titles in the platform section: the moving colour band is redrawn by the main thread on every frame.

Why "battery/heat only":
- Each redraw is small (a few ms), so it fits inside the frame's time budget (16.7 ms at 60 Hz). The frame is still delivered on time, so the scroll looks smooth.
- Your last finger run on the best build confirms it: almost no slow frames left in that part of the page (17 slow frames in 1000-5000 px, the platform section included).
- But the work still burns CPU every frame, even when you are not scrolling: with them, the platform section never goes idle (Chrome: 120 frames per 2 s; without them, 5). That is battery and heat.

Where it could still touch smoothness (not measured, so I won't claim it):
- Heat: a hot phone slows itself down. The one bad pin-hold stall we chase (F3) appeared only when the phone was at 40-43 °C. Less constant work means a cooler phone over a long visit, but we have no number for how much these two contribute.
- Budget sharing: if something else heavy happens in the same frame there (scroll work, layout), the redraw adds to it. Our runs show no such frames there today.

So they rank below the fixes that remove visible stutter. If you want them built anyway (as identical GPU versions), say so and they go after the current fixes.
