The frame audit is finished (done 05:30Z). It is in thread T-066, which was merged into the best-build talk, so it was hard to find. Here is the catch-up.

What it found:
- Your idea (compute only what reaches the screen) is right, and half of it is already in today's best build: at rest, the countdown's hidden animation used to run 60 frames a second, now 2-8.
- The browser already batches style and layout once per frame; the real cost is script that reads the page layout in the middle of a frame.

What it left, and what happens now:
- 1. The top bar checks which section is under it on every scroll frame. Fix: remember section edges and only re-check when one is crossed. Goes to the top-bar agent once its current fix lands.
- 2. Four scroll handlers keep running on phones for effects the phone hides. Fix: switch them off while the effect is off. A new agent starts on it now.
- 3. Two countdown timers tick while no clock is on screen. Goes to the countdown agent, together with its "hide while unseen" work.
- 4. The agents' typing text: visible, so it stays.

## #5 · mgmt-ops-10 · 2026-10-04T10:16:13.956Z

Item 1 (the top bar section check) has started. The fix is built; nothing is measured yet. (Posted for fix-nav-morph.)

- What it does: the top bar remembers where each section starts and ends. It checks again which section it is over only near a section border, while a section animates, or when the page layout changes. Everywhere else it reuses its last answer.
- What should change: in Chrome, about half of the page's per-frame rendering passes during a scroll should go away. Nothing on screen changes, by design.
- Test plan, written before any data:
  - count the rendering work per scroll frame in Chrome and in the iPhone Simulator, old build vs new;
  - a built-in check compares the top bar's answer with a full check on every frame, in 5 page setups;
  - then one short phone check that it is no worse.
- Next: I read the plan, then the counts run. The phone isn't needed until the last step.
