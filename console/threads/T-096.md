## #9 · arch-gpu-lessons · 2026-10-04T09:50:32.960Z

First results on why the new countdown feels smoother, and where else it helps.
- Why: each digit roll is now handed to the graphics chip as one finished animation, so no page script runs while it moves. Chrome and Safari both work this way; their own source code confirms it.
- The likely big one, if you felt it on the iPhone: Safari draws page script updates about 60 times a second, but it asks for 80-120 frames a second for animations handed to the graphics chip. So the new roll can be drawn up to twice as often. This is confirmed in Safari's source code but not yet seen on our phone. Apple says heat or Low Power Mode turn the faster rate off.
- On the Mac with the page at rest, the old roll was never held up, so there the gain is less work, not fewer stalls.
- The cost: on the iPhone, each roll's start and end costs one extra layer update. That matches the 1-2 extra slow frames per run in the phone check.
- Already moved to the graphics chip: the hero fade-out, the countdown, the platform glint and sweeps.
- Next candidates, in order:
  1. The hand-drawn accent word in the headline and its flicker. It's the last animation in the hero still run by the page itself. Older look-alike drafts exist; they would come to you as proposals with Try-it pages.
  2. The second clock in the end panel. It's already planned, the same change as the countdown.
  3. The end-of-page morph: the biggest moving area, but on hold. Its rounded corners can't be handed to the graphics chip in Safari today.
- Details: research/gpu-lessons/README.md.

## #10 · fix-cd-roll-ca · 2026-10-04T09:54:39.510Z

We found where the new countdown's extra slow frames come from. It's the moment a digit starts to roll, not the roll itself.
- On the iPhone, each slow frame (over 50 ms) landed on the exact frame where the top clock's digits start a new roll.
  - It's worst when two digits change at once and the last digit spins all the way from 0 to 9, which happens every 10 seconds.
  - Those frames were slow every time on the new countdown (3 of 3) and never on the old one (0 of 3).
- The rest of each roll is fine. The frames after the start are as smooth as the old countdown.
- Why the start is heavy (seen in the iPhone simulator; the cause is checked against Safari's source code):
  - At the start, Safari gets the whole movement path up front for every digit tile. That's up to 6,000 small steps on a 10-second tick, and Safari prepares each one before the roll can begin.
  - It also draws all the tiles of a spinning digit in that one frame, where the old countdown drew 1-2 per frame.
- Possible cheap fix, not built yet: describe the same path with far fewer steps (about 5 times fewer), with the exact same look.
- Next: one short iPhone check, to see which of the two costs is bigger. Also a separate check of whether the new roll is drawn at up to 120 frames per second on the iPhone, which may be why it feels smoother. Both wait for the iPhone after the current tests.
What you need to do: nothing.
