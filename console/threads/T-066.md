## #6 · mgmt-ops-10 · 2026-10-04T04:21:52.933Z

Yes, that's the direction the current fixes already take. Here's how it works and where its limit is.

**The frame budget.** 60 fps means one frame every 16.7 ms; 30 fps is 33 ms. Every moving element is drawn into the same page frame, so they can't each run at their own speed. One slow piece holds up the whole frame. Your goal stays: no frame over 50 ms, a steady 60.

**What can run in parallel (from the browser docs):**
- **Fully off the main thread:** moving, scaling, rotating and fading an element (transform and opacity), when it's done as a CSS or Web Animation. The browser hands these to a separate compositor thread and the graphics chip, so they keep running even when the page's script is busy. Chrome documents this as "compositor-only properties" (web.dev, "Stick to compositor-only properties"). Safari does the same through Core Animation.
- **Partly in parallel:** turning drawings into pixels. Chrome does this on helper threads and the GPU. Deciding *what* to draw (layout, style, paint) still happens on the main thread in both browsers.
- **Not in parallel:** the page's own script, which runs on one thread. A Web Worker can do math in parallel, but it can't touch the page's elements. It only helps for canvas drawing, which this page barely uses.

**What we do with it.** Each fix replaces "script recalculates the element every frame" with "describe the motion once and let the compositor play it":
- **Hero exit:** the slim version R2 is next on the phone (P-095).
- **End-of-page morph:** P-092.
- **Countdown roll:** P-093.

**Does moving to the GPU help? Yes, with a catch.** This morning's phone check (P-088) showed both sides:
- **Gain:** the script that moved the hero went from running in about 8 of 10 frames to about 2 in 100, with no extra slow frames.
- **Catch:** the switch onto the GPU path cost a burst of extra work the moment your finger starts a scroll. That's why it failed.

The GPU isn't free either. Every element it moves becomes its own layer, which costs memory and compositing work, and on the phone that means heat. So the rule is: put on the GPU only what actually moves, and keep the start of the move cheap. R2 is the version built on that rule.

The part that has to stay on the main thread is layout and style work. The other fixes cut that down (style work while the people cards scroll went from 118-123 ms to 59-65 ms per run on the phone).

## #13 · mgmt-ops-10 · 2026-10-04T04:35:16.635Z

You're right: fastwork.com is built with **Svelte** (SvelteKit). Its files sit under `_app/immutable/`, SvelteKit's default output folder.

**Svelte already does what that React page describes.** When several state changes happen together, Svelte applies them to the page in one go, not one by one (Svelte docs, `tick()`: "resolves once any pending state changes have been applied"). So batching state updates isn't where the time goes on this page.

**Where the time actually goes.** On the phone, most of each slow frame is the browser's own work after the script runs:
- **Style:** working out which CSS rules apply.
- **Layout:** working out where everything sits. On Safari this is often for the whole page.
- **Paint:** drawing it.

A frame's script part is usually small. What hurts is when one small script change makes Safari redo style or layout for the whole page.

**Your idea, "only calculate what the user can see", is the right one, and it's how most of our fixes work:**
- **Resting avatar row (P-094):** the slider stops its work while it is off-screen. Off-screen work was exactly what you describe: calculation nobody sees.
- **Idle animations (platform-idle, in the best build):** animations stop doing work when nothing on screen changes.
- **Countdown digit strips (landed):** the clock redraws only the digit that changes, not the whole clock.
- **Hero R2 (P-095):** script no longer recalculates the hero every frame. The browser plays a motion described once.

**What we can't do** is skip frames while something visibly moves. A dropped frame during motion is exactly the stutter you feel. The rule we use: during motion, do the minimum each frame; when nothing visible changes, do nothing.

**A possible next step, if you want it:** a page-wide check that lists every piece of script that runs each frame or each second, and whether its result is visible at that moment. The resting avatar row came out of a check like this for the "at rest" case. Say yes here and I'll pass it to the lead to schedule.
