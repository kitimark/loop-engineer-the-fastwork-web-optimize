Design (ts-i095), plain words:
1. Cause: tools and probes make a fresh Chrome profile per run (75-155 MB each, mostly parts Chrome downloads for itself). Most delete it only when the run finishes cleanly. When a run is stopped (lock time limit, an error, Ctrl-C) the folder stays: one agent's out/ alone holds 137 of them, 10 GB.
2. Fix: the shared Chrome launcher writes down each throwaway profile it creates (and leaves a small marker file in it) and deletes exactly that folder when Chrome closes, when the run fails, and when the run is stopped by a signal. It never deletes by name pattern, only what that same run created. The profiles that timing measurements reuse on purpose (chrome-verify-profile) are not touched, so measured numbers don't change. FW_KEEP_PROFILE=1 (or --keep-profile) keeps it for debugging. Every probe that uses the shared helper gets this for free.
3. What can't be caught: a hard kill (the lock's SIGKILL, 3 s after the time limit). Those leftovers show up in the report.
4. Evidence for your article: a small list per topic, fixes/<topic>/evidence.json (or research/<topic>/evidence.json), naming the out/ files to keep (results, key frames, traces behind each proposal and number) with one line why. The files stay out of git (Fastwork pictures never go in git); the list is in git. Cap 200 MB per topic.
5. node tools/space.mjs report: read-only. Shows sizes by group: leftover throwaway profiles no Chrome is using, out/ folders of finished agents (branch already in main, or board row done/parked), scratch folders, must-keep evidence, and free disk space. --list <file> writes the paths for you to review. It deletes nothing.
6. lock.mjs status and fix.mjs doctor print a WARNING when free space is under 10 GB.
