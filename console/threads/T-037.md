## #2 · lead · 2026-10-03T08:58:59.061Z

Our measurement rules, by phase. Every fix goes through 6 phases in order; none is skipped.

PHASE 1. RESEARCH: where is it slow, and how often?
- Find the slow frames on the iPhone (at least 3 runs with the same scroll method), plus Chrome at the phone's size.
- A slow spot that shows up in fewer than 2 of 3 runs goes on a "rare" list and isn't fixed until it's confirmed.

PHASE 2. INVESTIGATE: what changes in that slow frame?
- Which element, which style, which code runs at that point. Checked in both Chrome and Safari's engine.

PHASE 3. DISTINGUISH: what exactly causes it? (I sign this phase off.)
- Prove the cause: remove the suspected part and the slowness goes away; remove a neighbour and it doesn't.
- Any browser behaviour the explanation relies on must be confirmed by a reference (spec, Apple/Google docs, browser source code). Our own tests alone aren't enough.

PHASE 4. FIX: does the build do only what we intended?
- The fix is built on a frozen copy of the site. Never on the live site, never on the original files.
- Before any measurement, the agent writes down what it expects and exactly how the result will be scored. A second agent checks that. We never change a prediction after seeing data; if it was wrong, it stays recorded as wrong.
- Look must not change: pixel-identical to the original, checked by comparing screenshots. Only you can grant an exception.
- New since your decision today: a rendering cost report per fix (GPU or main thread, layers and memory, repaint area, layout, script), counted per event, from Chrome and the Simulator, with no phone heat.

PHASE 5. REVIEW: a real win on the target device, and nothing worse elsewhere?
- An independent reviewer tries to break the fix.
- Then the phone test: one phone, one test at a time. Original and fix alternate (C V V C ...), with a known-good control run to catch a hot or tired phone. Runs start warm (38-40 °C), all started the same way.
- "Does less work" fixes: the work counts plus one short phone check that nothing feels worse.
- Smoothness fixes (your top 3: hero fade-out, countdown strips, F3): phone test plus your own finger test.
- Things you decide go to you as a decision page or console step. Your decision is the spec.

PHASE 6. LAND
- I add it to the main version only after all of the above, and record which exact build was measured.

HOW SLOWNESS IS MEASURED
- Chrome is set to mimic your iPhone 15 Pro Max: same screen size, processor slowed 6x. That matches the phone's slow-frame counts.
- A "slow frame" on the phone is a gap over 50 ms (the goal is 0) or over 34 ms. Results right at the edge are flagged.
- Only results from the same tools and the same frozen copy of the site are compared.
- Timing tests on the Mac wait their turn, so nothing else runs while one is measuring.

## #4 · lead · 2026-10-03T09:01:26.216Z

The new measurement is the one from your idea in T-029 (#23, #25): measure what each element costs to draw, so we need fewer full-page phone runs and less cooling.

1. Isolated runs ("FRZ"). We freeze everything on the page except the one element we change (for example the countdown or the menu panel), then count its work. A normal full-page run ("FULL") is kept as a check, but needed less often.

2. A "cost card" for each fix. It has 5 rows, counted per event (per countdown second, per menu pin) rather than timed:
   - which thread does the work (main thread or GPU/scroll thread)
   - layers and GPU memory
   - how much area is repainted, and how often
   - layout work
   - script work
   Counts don't change when the phone is warm, so heat matters much less than with timing.

3. What the pilot showed (P-075, P-076):
   - Chrome: the style, layout and paint counts repeat reliably on the frozen page. These work.
   - Simulator: the counts repeat too, but frame-based counts (frames, style recalcs, compositing) only make sense on the full page. Those stay FULL.
   - Countdown script counts: not reliable yet, either per 4-second window or per countdown second (0 of 3 passed). For the countdown we still use the full-page numbers.

4. Safari on the Mac: we decided against it. Its layer and tile code differs from the iPhone's (checked in WebKit's source), and the Simulator already gives us the same layer and timeline data.

Where it stands now:
- A tool that builds these cost cards is being written (tools/costcard.mjs).
- The first fix to use it is fix 3 (the menu panel when your finger holds the end of the page). It gets a cost card before any phone test, with an extra row for the first time the panel pins.
- Under your "go with your recommendation" (#30), small heat fixes land on their cost card plus one short phone "no worse" check. Fixes 1-3 still get the phone test and your finger test.
- Running now: a 10-minute trial on the phone with Xcode's "Serious" thermal setting, to see how much heat alone changes the frame timing. I'll report the result in T-029.

Yes, they were updated after #4 (all by your decisions). The rules in force now, 03:15Z:

1. Cost card first (from #4, now built: tools/costcard.mjs). Each fix gets counted work (layers, repaint area, layout, script, which thread), on Chrome and the iPhone Simulator, before any phone timing test.

2. "Does less work" fixes land on their cost card plus one short "no worse" phone check (T-029 #30). New today (T-055): this now covers the countdown too. You said both versions feel smooth, so the countdown fixes need no more swipe A/B. Fixes 1 and 3 (hero fade-out, F3) still get a phone test and your finger test.

3. Phone tests start warm (T-039, option B): every phone test runs at the phone's real "Serious" heat state, checked with Xcode's thermal reader at the start and end of each run (a run outside Serious is repeated). We stop at 44 °C or "Critical". Before we call the goal done, each top-3 fix gets one short "no worse" check on a cooler phone (Fair).

4. Looks the same (PR-010): a fix must look identical, or within small fixed limits (colour shade up to 64 of 255, at most 0.5 % of the screen) in both Chrome and the Simulator. With reduced motion on it must be exactly the same. Anything beyond that, or a difference you only see while it moves, comes to you as a proposal (like PR-012 and PR-013).

5. Sleep (T-052, your answer today): the timing-test pause is lifted. A test cut by a Mac sleep is thrown out and repeated; two in a row and we stop until the Mac stays awake. Keeping the Mac awake for the whole session needs one step from you (see T-052 #5).

6. Unchanged: Chrome timing runs use the iPhone-like setting (430x932 screen, CPU 6x slower), one test at a time on the Mac, and every browser claim stays "OBSERVED" until a document or source code confirms it.

Next: after the countdown chain, milestone 2 (stay smooth from a hot start, 42-44 °C, and under Xcode-induced Serious).
