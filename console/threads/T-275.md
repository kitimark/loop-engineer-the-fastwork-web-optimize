## #10 · lead · 2026-10-12T11:55:51.545Z (asks)

Mostly yes: the cost comes from each engine's rules for what a change triggers, and most of those rules can be checked without the phone.
- Rules are in the source: which properties run off the main thread, which changes force layout, memory per layer (WebKit/Chromium code we cited).
- So 3 cheaper checks can come before the phone:
| Step | What it catches | Needs the phone? |
|---|---|---|
| 1. Rule check of the code (a linter) | layout reads in scroll, non-GPU animations, layer and blur size | no |
| 2. Simulator counts (same WebKit) | layouts, paints, layers per frame | no |
| 3. Cost model, tuned once on the phone | predicted ms per frame | once |
- Limits we measured: models missed the GPU floor (6-8 vs 3-4 ms) and heat; touch and perceived smoothness need a real finger.
- So the phone becomes the final check, not the first tool: in our study about 60-85 agent-hours went to Chrome wins that lost on the phone.
- Next step I propose: a small agent team builds step 1 (the rule checker) from our 30 lessons and tests it on the original page.

## #12 · lead · 2026-10-12T11:59:28.481Z (asks)

Core idea: turn the engines' rules into a cost table, then check source code against it; yes, it can run at build time.
- The table: for each CSS property, which stage a change costs (style, layout, paint, or GPU only), per engine, from the source we cited.
- Context decides the price: the same write is free once, but costly inside a scroll handler or every frame.
| Tool | Where it runs | What it does |
|---|---|---|
| Lint rules (CSS + JS + Svelte) | editor, CI | flag animated layout/paint properties, layout reads after writes in scroll code, huge blurs |
| Build plugin (fastwork is SvelteKit, so Vite, not webpack) | build | safe fixes only: image sizes/formats, passive listeners, report layers and blur area per element |
| Dev-mode probe | dev server, Simulator | count forced layouts and paints per frame, name the line |
- Auto-fix only what is provably the same look; most of our wins changed timing or look, so they stay warnings with a suggested fix (our pixel-identical rule).
- Similar checks exist in Chrome's tools, but Chrome-only; the WebKit rules are the new part (existing tools: to verify before we rely on them).
- The 30 lessons become the first rule set; the original page is the test: a rule must flag the code we fixed.
What you need to do: say yes to start a prototype (lint rules + dev probe first), or tell me what to change.
