## #4 · fix-cd-roll-ca · 2026-10-04T10:08:29.630Z

Short answer: the big frameworks don't solve this better. The ones that hand the motion to Safari either send many steps too, or use a format Safari can't run off the main thread. Our planned fix keeps the motion off the main thread and cuts the steps.
- Svelte: its built-in transitions send Safari one step per 1/60 s frame, close to what we do now. Its spring and tween helpers move things from JavaScript every frame, like the original countdown. (Checked in Svelte's source.)
- React: react-spring moves things from JavaScript every frame too. (Checked in its docs and source.)
- Vue and React with the Motion library (formerly Framer Motion): it sends Safari 2 steps plus a curve made of points, one point every 10 ms. (Checked in Motion's source.)
- Safari's source says a curve made of points can't run on the separate animation thread. It runs on the main thread, where scrolling also runs. Newer Safari code has an exception, but whether iOS 26.6 uses it is not known yet. (Checked in WebKit's source.)
- Our fix ("K"): it describes the same path with smooth curve pieces that Safari can run off the main thread. That is about 5 times fewer steps, and the look stays exactly the same. Building it now, then checked in the simulator and with a short iPhone check.
What you need to do: nothing.

## #5 · arch-gpu-lessons · 2026-10-04T10:18:27.154Z

The frameworks don't have a better trick for this. They all draw one smooth curve. Our countdown has to copy the original's stepped spring exactly, and the countdown agent's new version (K) does that with the fewest steps possible.

How each framework hands an animation to the browser (checked in each library's source and in Safari's and Chrome's source):

| way | who uses it | steps per moving thing | Safari: off the main thread? |
|---|---|---|---|
| start + end + one curve | CSS, Vue Transition, React with CSS, Motion tweens | 2 | yes |
| one step per 1/60 s | Svelte transitions | about 31 per 0.5 s | yes |
| points curve, linear() | Motion springs (React, Vue) | 2 + about 50 points | no |
| script every frame | Svelte spring, react-spring | none (all script) | no |
| our roll now (PR-017) | countdown | 144-343 per digit tile | yes |
| K, being built | countdown | 52-66 per digit tile | yes |

- **Why we need more than 2 steps.** The original roll jumps a different amount depending on exactly when the tick lands within a 1/60 s frame. One smooth curve misses it by 1 px on a one-digit roll and 12 px on a 0 to 9 roll.
- **Why K is the floor.** The original's path changes shape twice in every 1/60 s, so an exact copy needs one curve piece per shape. K uses exactly that.
- **Fewer steps would change the look**, by about as much as the original itself changes between a 60 Hz and a 120 Hz screen. If K's start still costs something, that could be a separate proposal for you to try later.
- **A side note on a newer Safari.** Its code has a new animation path, turned on 2026-09-26 but not in any Safari release yet. It would play these animations at 60 frames per second instead of 80-120, so part of the smoothness you felt may shrink in a future Safari. Unknown for now.
- **Correction to #4:** in Safari, scrolling itself runs separately. The points curve (Motion's linear()) runs on the main thread beside layout and script.
