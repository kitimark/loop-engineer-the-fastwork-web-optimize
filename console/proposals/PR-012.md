## Problem

Safari repaints the whole end-of-page panel on every frame of the menu morph.
- The morph: at the end of the page the small nav pill grows into the full dark panel.
- On phones every frame resizes the nav, so Safari repaints the title, photo columns, veil, footer and bar each frame.
Why you see this again:
- You accepted rev 1 on 2026-10-04. It was built on that day's best build.
- Today's build is v9-final, so the same reveal code was moved onto it.
- Today's build lays out the nav row a little differently, so a few edge pixels differ from rev 1.
- That is over our 'looks the same' limit, so you decide again.

## Idea

Two options, both on today's build v9-final.
- A: today's look, plus fix A only. Fix A is the end-of-page morph fix that repaints less. It changes nothing you can see.
- B: option A plus rev 1's reveal, the same code byte for byte.
- How the reveal works: on phones, while the morph moves, the panel is placed at full size once.
- Today's box is then cut out of it with a growing clip shape; text slides by a GPU transform.
Try it on the Mac now. The phone Try-it pages come after the current phone test ends.

## Options

### Option a: A: today's look (fix A only)

Keep the morph as it is today. Only fix A is added. It repaints less and changes no pixels.
- Try-it: the left page is today (v9-final), the right page is option A (today + fix A).

Risk: Low. Fix A's own phone check (no worse than today) runs now; it lands only if that check passes.

Visual difference:
- None beyond noise in our checks.
- One detail, one run each, cause unknown:
- Right after a close, today's build drew the 'Join waitlist' label 1 css px off in an older run.
- In option A's run it was in place.

### Option b: B: A plus the reveal (rev 1's change)

Option A plus the reveal you accepted in rev 1, the same code byte for byte.
- Phones only (640 px wide or less), and only while the morph moves.
- When it settles (fully open or closed), the extra styles are removed and the nav is exactly today's.

Risk: The first open after a page load may cost a few ms on the phone.
- Rev 1 cost about 6.5 ms more there (one test, ranges overlapping).
- Not measured on today's build yet; the phone check after your decision reads it.
- Not tested, as in rev 1: turning the phone, Android Chrome, lower pixel density phones, re-entering while the morph moves.
- Rev 1's Safari workaround (a one-frame blur switch when the panel finishes opening) is kept; its cause is still unknown.

Visual difference:
- During the motion, text and logo edges in the panel sit up to about 1 device pixel off from today, as in rev 1. Largest shade 236, on text edges.
- Size against option A (Chrome, 430x775, pixels over 8 shades):
- halfway (m 0.5): about 1,000 css px (0.3 % of the screen)
- m 0.8: about 10,000 (3 %); m 0.99: about 6,400 (1.9 %)
- today against itself: 0 to 44 css px
- Against rev 1: today's logo sits about 8 css px further left.
- So the edge differences land in slightly other places.
- New against rev 1: at most 492 css px (0.13 % of the screen).
- Shades up to 224 on edges; our limit is 64 fill / 128 edge.
- Part of those new pixels is the countdown digits: a tool artifact.
- Our two screenshot tools freeze the clock at different times, so the digits differ between the two checks.
- It is not a page difference.
- Per area (nav row, panel), the area and the largest shade of the differences are within a few percent of rev 1's at every step checked.
- After closing, the nav snaps to the pill, where today it eases a 0.2 px width change over 0.68 s (same as rev 1). It looks the same.
- Not checked on the real iPhone yet: a short phone check and a blind swipe A/B for you follow your decision.
