## Problem

Your note on rev 1: "the B is changed the visual. why we don't try to make them likes animation images frame or video likes apple.com did. let's research them."

1. "B changed the visual": agreed. The rev 1 wipe is dropped. Rev 2 shows the word's own pixels.
2. "animation image frames like apple.com": built and tested. The erase and the draw of 'you' were captured in Safari (Simulator, 3x) at every 1 ms of the 0.9 s, giving 2 x 901 frames. They are packed into one image and played on a canvas over the word, on the SVG's own animation clock.
3. "video like apple.com": researched; it can't match pixel for pixel. Safari's only transparent video, HEVC with alpha, stores colour at 4:2:0 (Apple, HEVC Video with Alpha Interoperability Profile: both layers Main Profile, chroma_format_idc 1). CONFIRMED.
4. "let's research them": what worked and what failed is below. Frozen frames match exactly. Live playback stalls in the Simulator, and so does a minimal page with no Fastwork code, so the Simulator can't tell us about the phone. Status: parked until a phone check, not withdrawn.

What it would remove: in Safari every frame of the stroke animation is a style + SVG layout change (WebKit source, F-097). Per 'you' draw in the Simulator today: 57.8 style recalcs, 57.3 layouts, 61.3 paints (Timeline counts, 4 draws).

## Idea

How it works (Safari only, by construction):
- Frames: only the 16 px tiles that change from one ms to the next are stored. That is one PNG (512x2291, 6023 tiles) plus a tile list for 'you'.
- Playback: a canvas sits on whole device pixels over the word. Each frame it takes the elapsed time from a Web Animation started with the SVG's own animations and copies the tiles up to that ms. The SVG stays underneath, hidden but still animating.
- Handback: the SVG takes over in the same frame, with the same timing, when you scroll (the canvas runs only at the very top), when the clock gives a time with no frame, or when the position check fails.
- Clock gate: the canvas runs only where the animation clock gives whole ms. WebKit floors it to 1 ms on pages that are not cross-origin isolated (Performance.cpp:73, timePrecision 1 ms; 20 us when isolated since d6c1e30075b7). fastwork.com sends COOP but no COEP, so it is not isolated. If COEP is ever added, the gate falls back to the SVG. Chrome's clock is fractional (Blink time_clamper 100 us), so Chrome keeps today's SVG.
- Loading: after the page's load event, at idle. The image is decoded (img.decode + createImageBitmap) before the canvas can take over, never during a draw. Until then the SVG runs.

What the phone check would test (not built yet; approve or reject):
- Arm 1, today's tile arm: 38-73 copies per frame on average, up to 195.
- Arm 2, one copy per frame like apple.com: every distinct frame stored whole. 'you' has 863 distinct frames, about 83 MB decoded and about 4 MB PNG (ESTIMATE). Test only: 7 words would need about 580 MB.
If arm 2 runs smoothly on the phone and arm 1 doesn't, a middle layout would follow: one box per changed ms, 5-10 copies per frame (max 17), about 18.6 MB per word (ESTIMATE). If both stall, we withdraw.

Your decision: approve the phone check (arm 1, plus arm 2 as a test-only build), or withdraw the frames route. The phone check needs the iPhone plugged in by USB (it is unplugged now).

## Looks the same?

Frozen frames, exact (OBSERVED, Simulator Safari 26.5): every 13th ms of the erase and the draw, 71/71 + 71/71 frames byte-identical to the original's own frames (word area 279x219 device px). Ink floor 500 px: 1 frame per direction is under it, and those match too. 0 blank frames. Repeat shots 6/6 the same. The canvas engaged in every frame.

Limits of that check:
- Each frame was drawn with the clock stopped, and read back with getImageData so the drawing was finished. Live playback does not wait like that, and live it does not keep up (see risk). So it does NOT look the same in motion today.
- Position was verified at the top of the page only. Whole-viewport parity was checked in Chrome only (no difference outside the countdown and photo-card boxes, which also differ between two loads of the original).
- Frames are captured per engine. Whether the Simulator's pixels equal the phone's is UNRESOLVED.

## Risk

Live playback FAILED in the Simulator (OBSERVED, cause unknown):
- Each canvas draw gets 0-9 frames instead of about 54, then the whole page stops rendering for 1-1.9 s. The page's own frame counter stops too. There were no script errors, and the page's script was idle (0-1 ms per frame).
- During the pauses Safari's WebKit GPU process runs at 73-100 % CPU (about 14 % otherwise). Canvas drawing runs in that process (WebKit source: WebChromeClient.cpp:1199-1206, GPU-process canvas on by default).
- The pause grows with the number of image copies. Hiding the SVG with no copies: no pause. One copy per frame: about 37 frames per second. A few thousand copies: a 15 s pause.
- In the Simulator, even a minimal page with no Fastwork code stalls in proportion to the number of drawImage calls from the image, with the WebKit GPU process at about 100 % CPU (OBSERVED, cause unknown). We therefore can't tell from the Simulator whether Safari on the phone stalls. That needs the phone, which we don't use before you approve.
- Memory: arm 2 would hold about 83 MB of decoded frames for 'you' alone (ESTIMATE), a real memory-pressure risk on a phone; that is why it is test-only.

Also tried, not chosen:
- A, CSS contain on the word: WebKit source REFUTES the saving.
- B, animate only the visible copy: smaller saving, and it is not the frames you asked for.
- Image-source and GPU-accelerated-canvas variants: their earlier runs relied on a URL flag the page drops, so they are void, including the observation that Chrome resampled an accelerated canvas. They were NOT re-run after the flag fix: hold 5 tested only hide-only, no-draw and one-copy.
- Video: 4:2:0 colour (CONFIRMED above).
Void results: earlier runs that relied on a URL flag (the page drops it) and the cached Simulator runs (F-115).

## Visual difference

- Frozen frames: none. 142/142 frames are the original's own pixels (filmstrip: top row erase, bottom row draw).
- Live in the Simulator today: the word freezes part-way through each erase or draw, for up to ~0.5 s, then jumps. Visible until a phone run shows otherwise.
- Chrome: no change. The clock gate keeps the original SVG.
