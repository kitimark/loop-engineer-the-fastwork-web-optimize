# PR-007: Countdown: 3 faces per digit, and no re-rendering while nobody can see it

## Problem

The countdown clock re-renders its rolling digits on every animation frame, even when it can't be seen: the hero clock after it fades out or scrolls away, and the second clock in the morph panel, which sits at opacity 0 for most of the page. Each digit is 10 stacked faces. On the full page in Chrome, past the hero, the main thread was busy about 760-815 ms less per 6 s with the change below (n=1, Chrome at 6x CPU, a CPU profile, not a timing A/B). In the iOS Simulator the hidden clocks cause about 100 extra layouts and 100 extra paints per 4 s past the hero (n=1, Simulator, not the phone).

## Idea

Follow apple.com's pattern (iPhone page, media-card gallery): animations play only while their scroll range is on screen, the page decides this from the scroll position, and only the cards next to the visible one are rendered. One difference: a countdown must show the current time, so on return it shows the frame an always-running clock shows, instead of continuing from where it stopped.

## Looks the same?

Checked with frozen frames in Chrome on the hero clock: the countdown's clock and frames are virtual and stepped identically in both versions, with frame times jittered by up to 1 ms like real ones and the 1-second tick falling mid-frame. 295 screenshots were compared byte for byte, plus the exact position of every visible face: rest, every phase of 6 kinds of roll at 60 Hz and 4 kinds at 120 Hz, and coming back after a fade-out, after scrolling away, after a tab switch and after two ticks while away. 0 of 295 differ; the baseline against itself also gives 0. The first frame after an instant jump back was read in 12 cases: 0 differ. Not shot: the panel clock, Safari/WebKit, a real 120 Hz screen.

## Risk

This replaces the earlier countdown fix #1 (countdown-idle-raf) in the same code: #1 snaps a hidden clock, which shows a different digit when the clock comes back mid-roll. The panel call site is shared with the morph lazy-mount fix (#13); when both land, the panel uses the stricter visibility condition. With hidden frames cheaper, Chrome at 6x renders more frames, so total style recalcs and paints for the page rise 10-25 % (less per frame). At the faded-out hero, layouts are +7 % and paints +13 %, cause unknown (n=3). While the clock is visible, about 1 small layout and 2 face repaints per second are added (a face slot changes its digit once per roll). The saving ends when the countdown expires (2026-11-02 05:00 UTC). Safari was checked for counts in the Simulator only; a phone check is needed before landing. No timing gain is claimed.

## Options

### Option full: 3 faces + no re-rendering while unseen

Each digit keeps 3 face slots instead of 10 (the two that can be in view plus one spare). While the clock is faded out, scrolled away or in the hidden panel, its spring keeps counting in the background but nothing is re-rendered; in the frame the clock is shown again it displays the value the original computes for the same frames. The hidden clock's spring still runs on every animation frame (about as many frames as today); only the re-rendering is skipped.

Risk: Touches the hero's fade-out code and the panel call site (shared with #13); replaces fix #1's version of the same code.

Visual difference:
- Nothing visible in the shots: 0 of 295 frozen frames differ, at rest, mid-roll and on coming back, including the first frame after a jump.

### Option pause-only: No re-rendering while unseen, keep 10 faces

Only the hidden-clock part: the spring keeps counting in the background while the clock is unseen and nothing is re-rendered; each digit keeps its 10 faces. This is fix #1's idea with an exact return instead of a snap.

Risk: No new layout or paint while visible, but the hero clock keeps its 80 face layers.

Visual difference:
- Nothing visible expected (same mechanism as 'full'; not separately shot).

### Option faces-only: 3 faces, always re-rendering

Only the 3 face slots; the clock keeps re-rendering while unseen, as today.

Risk: The unseen clocks keep re-rendering, so the main hidden cost (and the Simulator layouts) stays.

Visual difference:
- Nothing visible expected (same slot code as 'full'; not separately shot).

## Recommended

Option full: It removes the hidden re-rendering (the bulk of the cost) and cuts the hero clock's face layers from 80 to 24, with 0 pixel differences in 295 frozen frames in Chrome. Safari still needs a phone check before landing.
